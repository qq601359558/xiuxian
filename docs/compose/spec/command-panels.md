## §0 · 五步推演结论摘要（requirement-evaluator）与代码事实纠正

### 0.1 五步推演

**第一步 · 需求本质解构。**

- **表层需求**：「查看个人信息」等命令回复是纯文字、很乱，改成游戏面板效果；「很多其他的命令回复」也一样改。
- **本质意图**：不是「给文字加样式」，而是**把命令回复从「一段等宽文本流」升级为「可扫读的结构化信息面」**：卡片分区（信息分组一眼可见）、数值对齐（可比较的数排成一列）、关键字段可定位（找寿元/灵石/价格不再通读全文）。用户真正抱怨的是**信息密度与可读性的矛盾**——回复里明明有结构（境界/寿元/灵石/榜单名次/价格），却被压平成无差别的文本行。
- **关键目标**：① 个人信息类（/profile、/look）第一优先，必须做；② 高频 + 数据密度高的查看类命令全覆盖；③ 叙事类回复保持文本（叙事本身就是内容）；④ 桌面与手机同构（同一回复两端同一结构）；⑤ 只改呈现，不改数值、语义与叙事文本。
- **验收标准**：每个面板化对象在双端各有一张截图（卡片分区 + 数值右对齐/等宽可验）+ 服务端新增键的契约测试 + CLI 文本行为不变。

**第二步 · 可行性评估。** 可行，成本画像（实测，§0.2）：

- 服务端：`server/world.py:1172 handle()` 分发 189 分支；多数查看类命令的文本由既有格式化函数生成（如 `LeaderboardEngine.format_all`、`GoalEngine.format_board`），结构化数据**已在服务端内存里**，只需以新键随响应下发（只增键，不动文本生成逻辑）。
- 已有结构化键可直接复用、前端至今未读的至少 12 处：`profile`（/profile）、`here`（/here）、`goals`（/目标·/近况）、`agendas`（/议程）、`fate_thread`（/命途）、`fate`（/命格）、`art`（/自创功法）、`arts`（/功法）、`scan`（/探查）、`wallet`（/钱包）、`items`（/AI日志）、`commands`（/帮助）——见 §2 各行证据。另有 `status.*` 78 键（`_status_dict`，contract-audit census §3）可覆盖 /look、/图鉴、/坊市、/宗门环、/心法等面板的数据面。
- 前端：桌面 `web/workbench.js:6824 sendCmd` 通用路径是 `pushFeed(data.text)`（纯文本入 feed），特判只覆盖 /探险、/挖宝、/穿戴、/卸下、/突破、仪式、交谈、奇遇 8 类；移动 `web/mobile.js:1096 sendCmd` **无任何命令特判**，全部回复纯文本入 feed（见 F3）。因此本轮是「补通用面板渲染层」，不是逐命令打补丁：一个通用 feed 内嵌卡渲染器 + 每命令一张声明式字段映射（§3-D1/D2）。
- 性能开销：零新增请求；新键复用文本生成时已有的数据（或 `_status_dict` 已下发的快照），不新增 DB 查询（§4-K7 例外登记制）。

**第三步 · 不足与盲区。**

- **B1 · 目录 ≠ 分发全集**：目录 108 条（`core/command_catalog.py`，断言 `count==108`，`tests/test_command_catalog.py:52`）与分发 189 分支（contract-audit census §0）之间有 212 个分发独有 token：其中一部分是目录条目的子形态（如 /上拍 ⊂ /拍卖行），另一部分是**目录外真实命令**（/灵宠、/洞府、/心法、/行情、/版图、/钱包、/墓碑、/因果链、/委托、/诺言、/配方、/炼体、/炼神、/镇魔、/道统、/飞升榜等，见附录 B）。只清册 108 条会漏掉用户实际会点到的高频查看命令（/行情、/钱包都是纯文本大表）。处置：主清册 108 条全量 + 附录 B 对账全部分发独有 token，附录中的面板化对象同样立任务（§5 CP-49~CP-65）。
- **B2 · 文本即唯一数据源的命令**：约一半查看类命令只返回 `{ok, text}`（如 /榜裸查、/秘境、/宗门、/势力、/行情），结构只存在于服务端格式化函数的局部变量里。前端**禁止解析文本**拼面板（§4-K2），故每对象都须服务端先补键；补键字段须与文本逐行对账（数值、单位、空态三者一致），否则面板与文本两张皮。
- **B3 · 同名键语义冲突**：`/榜 <单榜>` 已返回 `board: <key字符串>`（`server/world.py:2565`），不是行集；裸查 /榜 只回 `text`（抓取 `047-ro-rank.json` 无 board 键）。新行集键不得复用 `board` 名（§4 附录 A 定名 `boards` / `board_rows`）。
- **B4 · 持久视图与回复面板的重叠**：洞府（renderSanctum）、宗门页（renderSect）、坊市（renderBazaar）、图鉴（renderGallery）、纳戒（renderInventory）已是状态驱动的结构化视图，但**回复本身仍是纯文本**（用户在 feed 里读到的是文本，不是视图）。处置：回复面板不重复渲染全量（§3-D4 全量卡 vs 摘要卡+跳转规则）。
- **B5 · 移动端预算已到硬线**：mobile.js 1645 行，距三期硬线 1660 行只剩 15 行；mobile.css 27395B，距硬线 27455B 只剩 60B（§7）。本轮移动端新增（通用渲染器 + 约 60 张面板声明）必然击穿硬线，**须先申请豁免再动 mobile 文件**（§7 申请数额与估算依据）。
- **B6 · 空态与单值回复**：大量命令在空态下只有一句话（如 /告示空栏、/宗门环散修态、/灵宠无宠态）。面板化须规定空态口径（一律不弹空卡，保留一行文本，§3-D6），否则满屏空卡比纯文本更乱。
- **B7 · /转世的目录描述与分发行为不符**：目录称 /转世「查看道统/转世出身加成」，但分发 `reincarnate()`（`server/world.py:1004`）活人调用只回 `{ok:false, error:"此世尚存，何须转世？可先 /道统 查看。"}`；真正的道统查看是目录外命令 /道统（`legacy_info` 全量结构键，抓取 `005-ro-legacy.json`）。处置：/转世归 (c) 类（转世执行 + 仪式已 (a)）；道统面板立在附录 B 的 /道统上（CP-62）。
- **B8 · 演示（demo）数据面**：桌面 `demoResult` 与 `state.demo` 门内存在本地捏造数据（contract-audit 台账 G 面已登记为 demo-only）。面板化只做联机路径；demo 路径沿用既有 demo 数据、不新增捏造，面板组件缺字段时显「—」（§4-K4）。

**第四步 · 举一反三。**

- **横向扩展**：同类问题不只命令回复——登录/入局（entry/origin_card）、仪式（ceremony）、奇遇（omen）早已是结构化卡片；本轮是把同一呈现语言**补齐到最后一块纯文本飞地**（命令回复）。通用面板渲染器建成后，后续任何新命令的查看类回复可直接声明字段映射接入，不再各自写渲染函数（防重复造轮子）。
- **纵向推演**：若未来命令继续增加（目录 108 → 更多），面板声明表与契约测试（`tests/test_command_panels.py`）是防回归资产：新命令默认文本回复、面板化须补键 + 补测试 + 补截图，三件套缺一不可（§6 验收门禁）。
- **涟漪效应**：① 服务端只增键，CLI 文本客户端零改动（CLI 仍读 text）；② 持久视图（sanctum/sect/bazaar/gallery）的数据源不变，回复面板复用同一 `_status_dict` / 响应键，不另建数据源；③ 契约测试沿 contract-audit 的 `tests/test_contract_audit.py` 体例（真实响应抓取 + 静态扫描），不另立测试哲学；④ 移动端预算豁免是本轮唯一须总管预批的门禁（§7、§11-D1）。

**第五步 · 完善方案。**

- 分四波交付（§5）：P0 个人信息（/profile、/look）→ P1 高频数据密度（17 项）→ P2 次高频（16 项任务，18 个条目）→ P3 低频/诊断/ gated（10 项）+ 移动端补齐（3 项）+ 目录外附录（14 项）+ gated 附录（3 项）。每波独立验收、可独立合并，不捆绑成一次巨型发布。
- 共存形态定为 **feed 内嵌卡**（§3-D1）：卡片嵌在 feed 流里、替代该条回复的纯文本块；对话框与仪式流不动（已有全屏流的命令不改形态）。
- 契约纪律沿用 contract-audit 轮（§4）：服务端是真相、只增键；前端只渲染、不解析文本、不捏造。

## §1 · Problem

用户在微信指出：查看个人信息等命令的回复是纯文字、很乱；期望是类似游戏面板的效果；且「很多其他的命令回复」同样如此。已承诺统一改成游戏面板样式（卡片分区、数值对齐），桌面和手机两端一起改。

现状（基线 2285d37 实测）：

1. **通用路径是纯文本**：桌面 `sendCmd`（`web/workbench.js:6824`）除 8 类特判外一律 `pushFeed(data.text)`；移动 `sendCmd`（`web/mobile.js:1096`）无任何特判，一律 `pushFeed(data.text)`。feed 里是等宽、无分区的文本流，数值（如寿元 70.4、灵石 100000、榜单分 63136.25）与叙事混排，无法扫读比较。
2. **结构化数据已在服务端、前端未读**：至少 12 个查看类命令已下发结构键而前端只取 `text`（§0.2-F2、§2 (b) 类「既有键」列）。最典型的是 /profile：`profile` 字典含 30+ 字段（境界/修为/灵根/寿元/道心/业力/功德/灵石/法门/小传/近日账录），前端一行未读，用户看到的却是 `═══ 审计员 ═══` 的纯文本块。
3. **已有面板只覆盖流程型命令**：仪式（ceremony 双幕）、宝图结算、探险（桌面）、交谈、奇遇选项条是结构化的；但**查看型命令**（榜单、行情、宗门、目标、议程、钱包、配方……）全是文本。用户高频查看的信息恰恰落在文本区。
4. **双端不一致**：/探险、/挖宝的面板桌面有、移动无；/望气·/奇遇移动端只有配图、无选项芯片（F3）。「两端一起改」须包含移动端补齐，不是桌面改完即算完成。

本轮只解决**呈现形态**问题：同一回复、同一数据，换成面板呈现。不解决数值、玩法、叙事文案本身的问题（见 §10）。

## §2 · 清册（先行，全量可复核）

### §2.1 枚举方法（不许抽样充数）

清册以**目录 108 条主命令**为一类口径（任务书指定），以**分发 189 分支**为对账口径（附录 B）。任何一条目录命令的归类都须同时满足以下四步，缺一步即为未完成：

1. **目录定位**：`core/command_catalog.py` 的条目（`cmd` / `aliases` / `desc` / `category`）；总数断言 `tests/test_command_catalog.py:52`（`count==108`）。

## §3 · Design（设计口径）

### D1 · 共存形态：feed 内嵌卡（默认；总管确认点，见 §11-D2）

- **默认形态是 feed 内嵌卡**：面板化命令的回复在 feed 流里呈现为一张卡片，**替代该条回复的纯文本块**（一处呈现，不并列两份）。卡片在 feed 中的顺序与原文本块相同（紧跟 `» /命令` 回显行之后），不插队、不置顶、不弹窗。
- **不动的形态**：① 仪式流（ceremony / ceremony_next 双幕：突破、挖宝得宝、转世）仍走全屏仪式卡；② 宝图 dialog（`#treasureStageBox`，/挖宝流）仍走 `openJadeDialog`；③ 交谈面板（/交谈·/说·/挂断）仍走交谈 UI；④ 奇遇/天象 inline 条（`renderInlineOmenBar`）仍走 inline 条；⑤ 入局卡 / 出身卡仍走既有容器。上述五类是 (a) 类既有形态，本轮不改其容器，只补其缺失的移动端部分（CP-46~CP-48）。
- **不新增的形态**：不新增对话框种类、不新开标签页/视图、不把回复搬离 feed。持久视图（sanctum/sect/bazaar/gallery/inventory）不因本轮新增视图；跳转只复用既有视图入口（`data-cmd` / 既有视图切换）。
- **文本字段仍下发**：服务端 `text` 字段一字不动（§4-K3）；CLI 与任何只读 `text` 的客户端行为不变。Web 端 feed 显示卡片而非文本块，是**前端呈现选择**，不是服务端行为变更。

### D2 · 双端同构

- 同一命令的面板在双端**同一结构、同一分区、同一顺序、同一字段**：分区标题、行集列、KV 键集合、空态文案、按钮组，两端逐项一致。只允许布局差异：桌面多列/宽表，移动单列/紧凑（行内数值仍右对齐）。
- 实现方式不限定（每端一个通用渲染器 + 同一份字段映射语义，或一端复用另一端的映射表），但**验收按双端截图逐项对照**（§8）：同一命令的两张截图须能逐行对上，缺一行即为双端分叉。
- 移动端补齐任务单独立项（CP-46 /探险、CP-47 /挖宝、CP-48 奇遇选项芯片），不得以「桌面已做」抵移动验收。

### D3 · 统一样式（沿用既有设计语言与 token）

- **设计语言**：宣纸为底、翡翠为骨、描金为线（mobile-redesign 轮定稿）；浅色默认 + 深蓝夜天象双主题。面板复用既有 card / 玉简条 / 品阶 pill / display-row 等组件与 class，新增 class 须复用既有 token。
- **数值对齐**：所有数值列**右对齐 + 等宽字体**（`font-mono` / `tabular-nums`，沿用既有 `fmtRemYearsUnit`、`treasurePanelStatLine` 的数值口径：2 位小数截断、不四舍五入进位造假值；缺失显「—」不带单位，沿 CA-005/M1 裁决）。
- **KV 行**：键左值右，键用次级色、值用主色；超过 6 行的 KV 块按语义分小节（小节标题 + 分隔线），不堆成一长列。
- **行集**：每行「主字段 + 右对齐数值 + 状态徽标」三段式；名次/编号列等宽；空行集不渲染空表（§3-D6）。
- **Token 纪律**：新增 CSS 必须全量 `var()` 引用 token（昼夜双 token 表），**零裸 hex**（沿 `test_mobile_redesign_tokens_and_no_bare_hex` 与 game-feel-phase2 §10；不在豁免内）。新增 class 命名沿用既有前缀（`panel-*` / `kv-*` / `row-*`），不得另立命名体系。
- **单位与符号**：灵石/修为/功德/业力等单位沿服务端文本口径（「灵石」「修为 +N」「功德 +N」）；正负号显式（`+N` / `−N`，不用 `+-`）；百分比 1 位小数。

### D4 · 全量卡 vs 摘要卡 + 跳转（防重复渲染规则）

- **全量卡**（默认）：行集 ≤12 行且文本等价长度 ≤800 字时，面板全量嵌 feed（§2.3 (b) 类多数项）。
- **摘要卡 + 跳转**：行集 >12 行或等价文本 >800 字，**且**存在可承载全量的持久视图时，回复只呈摘要卡（标题 + 3~5 个关键数 + 一行说明 + 「查看完整」跳转按钮，跳转到既有视图）。适用：/图鉴（139 行 → 图鉴视图）、/坊市（数十行货单 → 坊市视图）。摘要卡不得只剩一个按钮（至少含 3 个关键数），否则与纯文本无异。
- **无持久视图的大行集**（如 /帮助 108 行、/世情 40+ 行）：全量卡 + **分类折叠**（默认展开首区、其余折叠；移动端默认只展开首区）。折叠是纯前端状态，不发请求。
- **判定责任**：实现岗在任务内写明所选形态与行数依据；评审按本条复核，形态选错（该摘要的做了全量、该全量的做了摘要）视为 must-fix。

### D5 · 交互（只读为主）

- 面板默认只读。可交互元素只限以下四类，且全部复用既有机制、不新增命令与端点：① 跳转按钮（既有视图切换 / `data-cmd`）；② 快捷命令芯片（`data-cmd="/命令 …"`，如 /here 行的「交谈」芯片发 `/交谈 <名>`）；③ 折叠区展开/收起（纯前端）；④ 选项按钮组（/回应、/寻宝、/命格待选、/宗门环接取：按钮发**既有命令**，服务端落账路径一字不动）。
- 面板内不得出现：新输入框（除既有命令框外）、新确认流程、新排序/筛选控件（首轮不做；排序筛选若后续需要另立 Spec）。
- 点击行集中的人名/物品：有既有点击行为的复用（如同场头像开聊），无既有行为的不新增点击（纯文本行）。

### D6 · 空态与缺失口径

- **空态不弹空卡**：行集为空时，回复保留一行文本（如「告示栏空空如也。」「眼下无因果缠身。」），不渲染空面板。KV 块全空时同理。
- **字段缺失显「—」**：结构键在场但某字段缺失/null 时，该行显「—」（数值列）或整行省略（描述性行）；**不得**以前端默认值填充（沿 CA-005/CA-006 裁决：`s.merit || 3650` 类假缺省是 P0 级捏造，已修；本轮新面板同禁）。
- **零值是值**：0 必须渲染为 0（`??` 判空，不用 `||`）；`0` 与缺失严格区分（CA-006 返工裁决）。

### D7 · 性能与无新增请求

- 面板化不新增任何网络请求：面板只读当次响应 + 当次 `status` 快照。服务端新键复用文本生成时已有的数据或 `_status_dict` 已有快照；如某键确实需要新查询，须在任务内登记（§4-K7 例外登记制），实现岗不得静默加查询。
- 前端通用渲染器须为纯函数式映射（输入响应对象 → 输出卡片 HTML），不得在渲染内调接口、不得在渲染内写状态（除折叠 UI 状态外）。

## §4 · 契约纪律（沿 contract-audit 轮；服务端是真相）

- **K1 · 服务端只增键**：每个面板化对象的新键见附录 A。分发层只透传引擎/格式化函数已有的数据；**不动既有文本字段**（`text` 生成逻辑一字不动）、**不动数值语义**（数值、单位、进度口径、空态判定一字不动）。既有键名被占用时另起名（如 /榜 `boards` / `board_rows`，不得复用 `board` 字符串键，F6）。
- **K2 · 禁止前端解析文本拼面板**：前端只读结构键渲染面板。禁止 `split` / 正则 / 子串截取 `text` 字段拼数值、行集或选项；禁止以 `text` 内容推断状态（如 `stone_gain === 0` 推断无扣款，CA-002 同型错误）。契约测试以静态扫描锁定（§6-AC-05：新面板代码中不得出现针对 `text` 的行集切分模式）。
- **K3 · CLI/文本客户端行为不变**：`text` 字段、命令语义、错误文案、退出码（CLI 侧）全部不变；CLI 渲染（`cli/views.py` `render_*`）零改动。Web 端 feed 显示卡片是前端呈现选择（§3-D1），不改变响应契约。
- **K4 · 禁止本地捏造**：面板字段缺失时显「—」或省略（§3-D6），不得以前端写死值、demo 种子值或推断值填充。demo 路径（`state.demo` 门内）沿用既有 demo 数据，不新增捏造；联机路径不得读 demo 数据。
- **K5 · 数值呈现口径**：沿 CA-005/M1：`rem_years` 类 2 位小数服务端值前端 `toFixed(1)` + 单位「载」，缺失整串「—」不带单位；其余数值 2 位小数截断（`treasurePanelStatLine` 口径）；货币/计数用千分位分隔与否沿既有同类面板（榜单分、灵石价）保持一致，不得混用。
- **K6 · 既有契约不回退**：contract-audit 轮的 `tests/test_contract_audit.py`（30 测试）与 `tests/test_game_feel_phase3_frontend.py`（含预算硬线）全绿（基线失败除外并逐条注明 PRE-EXISTING）；本轮新增 `tests/test_command_panels.py`（§6-AC-05），不改既有断言数值（预算豁免除外，见 §7，须总管批准后同步修订并注明出处）。
- **K7 · 新查询例外登记制**：新键所需数据若不在文本生成路径与 `_status_dict` 快照内，须在对应任务内登记「新增查询：表/条件/频次」，由评审确认无 N+1 与无 tick 扫描；未登记的新查询视为超纲。
- **K8 · 键命名**：新顶层键用既有风格的小写下划线（`boards`、`sect_orders`、`npc_goods`）；行集元素字段名与服务端模型字段一致，不得为前端另起别名；新增键随附录 A 登记（键名/形态/来源函数/空态），未登记的键不得上线。

## §9 · 风险与兜底

- **R1 · 移动端估算漂移**：字段映射行数可能超估算（某面板字段特别多，如 /世情七区、/行情四区）。兜底：映射表按区拆行仍计入估算；超新上限 2100 行 / 29200B 时停工回主策岗，不得静默压缩既有代码腾挪空间。
- **R2 · 新键与文本对账漂移**：文本由格式化函数生成、新键由另一处组装时，两处可能分叉（如 /榜单榜行集与 `format_all` 文本）。兜底：契约测试以真实响应抓取逐行对账（数值、单位、空态三者）；评审抽查 ≥5 个面板的键-文逐行对照。
- **R3 · gated 项抓不到非空态**：/交易进行中态、/师门任务有师父态、/名物非空态、/议政有宗门态、/结义任务有结拜态、/npc货单有参态可能在测试环境难以构造。兜底：各 gated 任务写死门禁（先抓后定；抓不到暂停回主策岗）；不得以前端臆测字段上线。
- **R4 · 摘要卡信息不足**：/图鉴·/坊市摘要卡若关键数选错，用户仍须跳视图才看得到数，等于没修。兜底：摘要卡至少含 3 个关键数（§3-D4）；评审按「不跳转能否回答用户最常问的 3 个数」复核。
- **R5 · /穿戴·/卸下本地乐观改状态（既有模式，不属本轮）**：`handleEquipAction` 先改本地 `state.equipped/inventory` 再调服务端（F7）。本轮不碰该模式；若评审发现面板化后该模式与新面板数据面冲突，另立工单，不在本轮顺手改。
- **R6 · /退出 web 路由缺口（既有问题，不属本轮）**：目录有 /退出（aliases /quit），CLI 本地处理（`cli/main.py:537`），服务端 `handle()` 无 /退出分支——Web 端输入 /退出将回未知指令。面板化不适用（无数据面）；记为发现项，见 §11-D5，由总管另行裁决是否立工单。
- **R7 · 持久视图与回复面板双数据源**：回复面板读响应键、持久视图读 `status`，同一数据两处来源可能在同一次响应里不一致（如 /命途 `fate_thread` vs `status.fate.thread`）。兜底：契约测试断言同源键逐字段相等（取响应键为准，`status` 为辅）；分叉时报给后端岗补齐，不得由前端二选一掩盖。
