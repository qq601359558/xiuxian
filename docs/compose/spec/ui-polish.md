# Spec：web 前端 UI 优化（ui-polish）

> 状态：Spec（阶段一产出，待总管确认后交前端岗实现；本文件不含业务代码改动）
> 基线：`ee9a645`；隔离分支 `feat/ui-polish`，工作区 `.worktrees/ui-polish`
> 依据：仓库根 `AGENTS.md` 阶段一 + `.agents/skills/requirement-evaluator/SKILL.md` 五步推演
> 范围：只动 `web/` 前端（`index.html` / `app.js` / `style.css` 及 `web/` 内静态资源）。
> 本 Spec 是验收的唯一依据；Spec 外的功能一律进 Out of Scope 或另立工单，不得边写边扩。

## §0 五步推演摘要（requirement-evaluator）

### 0.1 需求本质解构

- **表层需求**：「优化 UI」——更好看、关键信息一眼可见、手机能用。
- **本质意图**：这不是换肤。当前 `web/` 已经有一套夜空墨青 × 金印 × 灵玉的视觉语言
  （`style.css` `:root` 配色、衬线标题、卡片 + 毛玻璃），但它是**在功能迭代中拼出来的**：
  命盘、行囊、死亡结算、钱包是四次不同批次（灰度 B、F01/F02、account-death T13）叠加上去的，
  各自沿用旧样式、各自处理降级，导致三类断裂：
  1. **视觉断裂**：同一类信息（数值、状态、金额、操作）在不同卡片里字号、间距、颜色口径不一，
     读起来像临时面板拼盘，而不是同一款游戏的 HUD。
  2. **信息断裂**：三条主线（寿元 / 因果 / 势力）中，寿元只有数字 + 一条以 100 为满槽的近似条，
     因果只有「业 / 德」两个数字（`dao_heart` 已下发却未渲染），势力只有宗门名，
     玩家无法一眼判断「我离死多远、我现在是什么处境、我属于哪方势力、主导与否」。
  3. **流程断裂**：手机 / 平板下右栏直接消失（见 0.3 第 5 点），等于丢掉半个游戏；
     失败与防重复提交只在个别入口（转世、钱包）做了，多数按钮没有。
- **系统定位**：纯表现层重构。数据流不动：唯一数据源仍是 `/action`（`/look`、`/here` 等）
  响应里的 `status`（`server/world.py` `_status_dict`），登录 / 死亡 / 转世仍走现有
  `/register` / `/login` / `/action`；不新增、不修改任何服务端接口与数据语义。
- **验收标准**：见 §5。每条都是可观察的：打开某界面、做某操作、看到某呈现、
  字段缺失时看到某降级——而不是「感觉更好看了」。

### 0.2 可行性诊断

- **技术可行性：高**。全部是 `web/` 内 HTML 结构微调 + CSS 变量 / 布局 + `app.js` 渲染逻辑，
  无构建工具、无外部依赖、无新服务。现有文件共 3183 行
  （`index.html` 495 行、`app.js` 1647 行、`style.css` 1041 行），改动面可控。
- **系统影响面**：仅 `web/index.html`、`web/app.js`、`web/style.css` 及 `web/` 内静态资源。
  另有两条硬性关联，见 §2.6 与 §6：
  1. `tests/test_qa2_frontend_contract.py` 断言「`app.js` 读取的 `status` 键 ⊆ 后端下发键」——
     前端**只能读已有字段**，读了新字段即破回归测试；这是本 Spec「不新增接口」在测试层的硬约束。
  2. `tools/public-entry-proxy.js` 以相对路径托管 `web/` 并代理 API——前端不得改用绝对资源路径、
     不得引入 CDN，否则公网单入口部署即断。

### 0.3 不足、盲区与风险（推演中发现，全部已在本 Spec 中闭环）

1. **寿元条是近似值，却长得像精确比例**（盲区，§4 G1）：`status` 只有 `rem_years`，
   没有寿元总量；现有条宽 `rem_years / 100` 只是「以 100 岁为满槽」的相对长度。
   若标成百分比或「寿元进度」，就是在用前端捏造分母。闭环：数字为准、条只作相对长度、
   不得标注百分比含义（U05）。
2. **地点「安全」是推断，不是事实**（缺陷线索，§4 G4）：现有 `zoneTag` 在非闭关、非冲突区时，
   只要有 `location` 就写「安全」。但地点安全与否以 `config.py` `WORLD_LOCATIONS[].is_safe` 为准，
   且 `status` 根本不下发该字段——黑风绝渊一类凶地也会被标成「安全」。闭环：无显式字段时
   不得断言安全，改中性呈现（U09）。
3. **势力主线在 `status` 里只有一半**（字段缺口，§4 G3）：有 `sect` / `rank`，无区域、
   无主导宗门、无影响力、无九五折生效标志。前端无法从 `status` 回答「此地谁主导、我是否享折扣」。
   闭环：只呈现宗门归属行；主导信息只走已有 `/版图` 文本结果，不解析、不捏造徽标（U07）。
4. **因果刻度缺失**（字段缺口，§4 G2）：`sin` / `merit` 为无界整数，无上限、无净值定义；
   `dao_heart` 有 0–100 的模型口径（`core/models.py` `KarmaLedger` 默认 100）却未被渲染。
   闭环：业 / 德只作双数字 + 血煞标志；道心单独作 0–100 条并钳制，缺失则整条隐藏（U06）。
5. **移动端右栏直接消失**（最大功能缺口）：`style.css` 在 `≤1100px` 时 `.rail.right { display: none; }`，
   宗门 · 坊市、秘境、灵宠、洞府灵田、同场修士整组功能在平板 / 手机上不可达，
   且无任何替代入口。闭环：任何宽度下右栏功能必须可达，至多 2 次操作到达（U18）。
6. **防重复提交只做了点状入口**：全局 `send()` 有 `busy` 守卫（第二次调用只记一行「天道正在裁决」），
   但视觉上只有 `btnJoin` 被禁用；`btn-soft` / `chip` / 行囊按钮在等待期间无 disabled / loading 态，
   玩家无法区分「没点上」与「正在裁决」，容易连点、重复下单。闭环：触发控件本身进入
   disabled + loading 态，失败后恢复（U15）。
7. **失败会丢输入**：聊天 / 奇遇自由输入在发送前就被清空，失败后草稿不可找回；
   钱包、转世虽已保留输入，但未形成统一规则。闭环：失败 = 就地提示 + 保留输入 / 选择 + 不跳转（U15）。
8. **重复的「接令」入口语义冲突**：世界页与坊市区各有一个 `data-prompt="接令"` 按钮，
   占位文案却不同（世界页「凶犯道号」vs 坊市区「告示编号」，命令前缀同为 `/接令`）。
   改命令语义在 Out of Scope；
   闭环只在前端文案层消歧：标题 / 提示写清各自前置条件（世界页：先点「除凶」看凶犯；
   坊市区：先点「告示」看告示编号），不改命令本身（U16）。
9. **小目标未达标**：`btn-soft` 最小高 36px、`chip` 32px、同场操作按钮 28px，
   均低于 44px 可点区域要求；`body { overflow: hidden }` + 三栏固定布局在窄屏下容易横向溢出。
   闭环见 U19、U20。
10. **对比度未经核验**：`--muted: #7d7a70` 等次要文本以 11–12px 出现在深色底上，
    是否达到正文 4.5:1 未在代码中留证。闭环：实现岗必须实测并写进验证记录，
    不达标就调亮，不得凭感觉放行（U23）。
11. **双端语义**：本任务只动 web 端。CLI 不受影响，但同一行为（如钱包提取、转世）在两端
    的文案与失败语义不得分裂：web 端的金额、单位、提示口径须与服务端返回文本一致，
    不得在前端重算余额、重算合计（U12、U14）。

### 0.4 举一反三

- **横向**：命盘钱包行、死亡结算钱包区、转世指引三处都在讲「同一笔钱包钱」，
  却用了三套排版与文案。应收敛为一套「钱包呈现模式」（户名 + 余额 + 最近 5 条流水 + 提取入口），
  三处复用同一模式，只在详略上分层（U12、U14）。同理，状态 pill（新手庇护 / 血煞 / 大限 /
  冲突区 / 闭关）与地点标签应收敛为同一套状态色与文案口径（U09）。
- **纵向**：今天缺的三个字段（寿元总量、区域与主导、因果刻度）未来若由后端补齐，
  前端应只需「有字段则显示真比例 / 真徽标，无字段则降级」，而不必重构。
  因此本 Spec 把「字段存在性检查」写成每条验收的标配（`if (field != null)` 才渲染），
  为后续后端补字段留出零重构的接入点（§4）。
- **涟漪**：改布局与改 DOM 结构会波及两类外部依赖——回归测试对 `status` 键集合的断言
  （0.2），以及玩家已保存的 `localStorage`（`td_base` / `td_token` / `td_user` 等键名不得改）。
  本 Spec 因此把 DOM id 与 `localStorage` 键名都列为兼容清单（§2.6）。

## §1 Problem：现状审计（读代码所得）

### 1.1 现有视觉语言（可用，但未统一执行）

- `web/style.css` 已定义：`--bg #0a0d12`、`--gold #d4af37`、`--gold-soft #e8c96a`、
  `--jade #3ecf8e`、`--blood #ef6b6b`、`--paper #f2e8d0`、`--text #c9c4b6`、`--muted #7d7a70`；
  衬线（`Noto Serif SC` 等系统回退栈）用于标题 / 数值，`--r: 14px` 圆角，
  卡片为半透明表面 + 金线边框 + 阴影。入世页（金环「道」字）与主界面 HUD 已有游戏感。
- 但执行不统一：命盘 `kv` 行、钱包行、死亡结算行、行囊行、世界频道、同场卡片各自定义间距与字号；
  状态色散落在 `.pill`、`.tag`、`.note`、行内 `style.color`（如寿元 `<10` 岁变红、心魔 `stage>=3` 变红）
  等多处，无统一的状态色表；按钮有 `btn-primary` / `btn-soft` / `btn-mini` / `chip` / `btn-icon`
  五套，却只有 `btn-primary` 有 `:disabled` 样式。

### 1.2 三栏布局与响应式现状

- 桌面：`.shell { grid-template-columns: 260px minmax(0,1fr) 280px }`，左命盘、中天道录、右场景。
- `≤1100px`：右栏 `display: none`，HUD 宽格（寿元 / 修为条）隐藏——平板上寿元条与右栏功能双双消失。
- `≤780px`：左栏变横向滚动行（卡片 `min-width: 240px`），主舞台在下方；`body { overflow: hidden }`
  下窄屏仍可能出现横向溢出与点不到的按钮（见 0.3 第 9 点）。

### 1.3 核心流程现状

- **登录 / 入世**（`#gate`）：服地址 + 登录 / 注册 tab + 用户名 / 密码 / 道号（注册时显），
  主按钮 `btnJoin`，错误进 `gateMsg`；已有 `busy` 时禁用 `btnJoin`。服地址预填逻辑在 `app.js`
 （见 §2.6），但 HTML 里仍写着 `value="http://127.0.0.1:8765"` 的硬编码初始值。
- **命盘**（`.card.fate`）：头像字、境界、修为条、寿元条、`kv` 十行（灵根 / 位置 / 随身 /
  金库 / 账户钱包 / 业·德 / 灵气 / 天象 / 心魔 / 灵宠）+ 状态 pill + `walletBox`
  （余额、户名、最近流水 `<details>`、提取表单）。`dao_heart`、`sect`、`rank`、`quest`、
  `body_soul`、`books`、`cave` 已下发但命盘未用或只在别处用。
- **行囊**：`renderBag` 按「已穿戴单独成行 + 库存同名合并 ×n + 阵盘行 + 法门行」渲染，
  每行带穿戴 / 服用 / 卸下 `btn-mini`；空囊显示「行囊空空」。
- **死亡结算与转世**（`#deathModal`）：死因 + 享寿、道统点与历世数、加成选择（至多 `max_boosts` 项）、
  资金归集明细（随身 / 寄存 / 拍卖退款逐单 / 当票没收 / 议政作废 / 合计）、寄售待结提示、
  钱包余额与流水、转世三要素指引、新道号输入 + 转世 / 暂不转世。
  已有良好模式：转世失败时 modal 保持打开、道号与加成原样保留、错误进 `deathError`；
  暂不转世后不自动建角（account-death §2.6）。本 Spec 要求把这一模式推广为全站规则（U15）。
- **指令体系**：按钮为主、指令栏默认收起（`高级敕令` 切换）；`send()` 全局 `busy` 守卫；
  `promptModal` 负责带参命令；聊天 / 奇遇 / 心魔各有 modal。

## §2 Design

### 2.1 设计原则（实现岗不得违背）

1. **游戏 HUD，不是营销页**：信息密度优先于留白与插画；长时间游玩（闭关、刷频道、看榜）
   不疲劳、不闪烁、不抢戏。装饰层（`.sky`、`.motes`、金环）只作背景，`aria-hidden`，
   且遵循 `prefers-reduced-motion`（已有，不得删）。
2. **数字为准，图形为辅**：一切条、刻度、状态色旁边必须有数字 / 文字值；条宽变化
   不得单独承载含义。禁止「只用颜色 / 只用图标 / 只用图片」表达生死、金额、境界等关键信息。
3. **状态色全站统一**（在现有变量上收敛，不引新色系）：
   金（`--gold`）= 主操作 / 境界 / 资产正向；玉（`--jade`）= 安全 / 完成 / 庇护；
   血（`--blood`）= 危险 / 死亡 / 血煞；橙（现有 `#f0a060` 档）= 警告 / 大限将至 / 冲突。
   同一语义在 HUD、命盘 pill、地点标签、日志行中必须同色、同文案。
4. **层级三档**：主操作（登录、转世、突破、提取）用 `btn-primary` 级视觉；
   常规操作用 `btn-soft`；行内次要操作（穿戴 / 卸下 / 服用）用 `btn-mini` 级，
   但可点区域仍须达标（U19）。危险操作（斗法、叛门、放生、弃令）须有确认或二次提示，
   沿用现有 `confirm` 模式，不得静默执行。
5. **失败不回退、不丢数、不造数**：任何失败都就地提示、保留输入与选择、不跳转、不清空、
   不改动已渲染的余额与数值（钱包提取失败余额不变是已有正确模式，推广到全站）。
6. **离线可用**：零构建、零 CDN、零外部字体下载；`web/` 内只用相对路径资源，
   保证 `tools/public-entry-proxy.js` 静态托管 + 公网隧道下同样可用。

### 2.2 视觉系统（目标 1 的落地口径）

- 以现有 `:root` 变量为唯一色板与字阶来源；新增变量只允许为「状态色 / 间距 / 字阶」
  的语义化别名（如 `--state-danger: var(--blood)`），不得另起一套配色。
- 字体层级收敛为四档：标题（衬线、金色、字距）/ 数值（衬线或等宽，纸色）/
  正文（无衬线、文本色）/ 次要（无衬线、`--muted`、11–12px，且须过对比度验收 U23）。
  数字单位统一：灵石、岁、级、x（灵气倍率）不得混写或省略。
- 卡片 / 面板质感统一：同一圆角档、同一边框（金线弱线）、同一阴影档、同一内边距档；
  命盘、行囊、钱包、死亡结算、弹层不得再各自定义一套卡片样式。
  行与行之间用弱分隔线，不用大面积色块堆叠；长列表（行囊、同场、世界频道）保持
  现有滚动容器与 400 / 80 条截断口径不变（性能口径，不在本任务中改）。

### 2.3 关键信息可视化口径（目标 2；字段依据见 §4）

- **寿元**：数字 `rem_years`（保留 1 位小数显示，单位「岁」）为准；条为相对长度
  （沿用 `rem_years / 100` 钳制 0–100 的现有算法，但**不得标注为百分比或总寿元占比**）；
  状态色只用可信阈值：`lifespan_warning == true` 或 `rem_years < 10` 时血色 +「大限将至」，
  其余金色。HUD 与命盘两处寿元必须同值、同色、同阈值。
- **因果**：业 / 德双数字并排（`sin / merit`），血煞时（`blood_marked == true`）加血色标志；
  道心单独一条 0–100（`dao_heart` 钳制 0–100，缺失则整条隐藏，不显示 0 或假值）；
  心魔沿用现有 `heart_demon_state.stage / stage_name / seed` 文案与三档色（`stage>=3` 血、
  `stage==2` 橙、其余默认）。业 / 德**不得**合成一条「善恶进度条」（无净值定义、无上限，合成即捏造）。
- **势力**：命盘势力行 = `sect`（空则「散修」）+ `rank`（空则不显示职阶，不写假职阶）；
  位置行只写 `location` 原文。**不得**出现主导宗门徽标、影响力条、折扣徽标——`status` 无此字段。
  玩家想查主导：点已有「版图」按钮，读 `/版图` 文本结果（世界页文本区），前端不得解析该文本
  生成徽标（文本格式非契约，解析即脆弱耦合）。
- **修为 / 灵气**：修为条只在 `exp` 能解析为 `cur/max` 时显示，否则只显示原文；
  灵气行必须标注为「全服灵气」（`qi_mult` 为全局倍率，非个人属性），不得写成个人灵气值。
- **钱包**（三处复用同一模式）：户名（`wallet.username`，空则用登录用户名，仍空则「—」）
  + 余额（`wallet.balance`，单位灵石）+ 最近流水（`entries` 或 `ledger`，最多 5 条，
  文案与 `walletKindCn` 映射一致）+ 提取入口。余额只读渲染，提取成功后以服务端回包刷新，
  失败时余额纹丝不动。

### 2.4 核心流程口径（目标 3）

- **登录 / 入世**：层级 = 服地址（次要）< 用户名 / 密码（主输入）< 登录 / 注册主按钮；
  注册时才显道号行（现有行为保留）。校验失败（空用户名、密码 <6 位）就地进 `gateMsg`，
  不发请求；服务端失败同样就地显示，不跳转、不清空密码以外的输入；请求期间 `btnJoin`
  disabled +「登录中… / 注册中…」文案（现有行为保留并推广）。
- **命盘（含钱包行）**：信息分层 = 头像 + 名 + 境界 → 寿元 / 修为条 → 状态 pill →
  `kv` 明细 → 钱包盒。钱包盒默认收起流水（`<details>` 现有行为保留），提取表单与
  余额在同一视觉组内，不得把提取入口藏到二级页。
- **行囊**：已穿戴行、库存行、阵盘行、法门行的现有语义与顺序保留；
  空囊、空法门、空流水三态必须有文字空态（不得空白一片）；行内操作按钮失败时
  行本身不消失、不错位。
- **死亡结算与转世引导**：顺序固定为死因与享寿 → 道统与历世 → 资金归集明细 →
  寄售待结提示 → 钱包余额与流水 → 转世三要素指引 → 加成选择 → 新道号 + 转世 / 暂不转世
  （现有顺序保留）。转世是唯一主操作，视觉最突出；暂不转世为幽灵按钮，不得弱化到看不见，
  且点后必须给出去向提示（现有「下次登录可回到此页转世」文案保留）。
- **失败与防重复提交（全站统一规则）**：触发控件在请求期间进入 disabled + loading 态
  （文字或转态示意，不得只靠光标）；`send()` 全局 `busy` 守卫保留（二次触发不发请求，
  给可见提示，不记为错误）；任何失败：错误文案出现在触发点附近（表单下 / modal 内 /
  feed 错误行三者至少其一），输入与选择原样保留，页面不跳转，modal 不自动关闭。

### 2.5 移动端与一致性口径（目标 4、5）

- **断点**：沿用现有 `1100px / 780px` 两档，不得新增断点体系（避免与回归测试外的布局假设冲突）；
  但两档的**行为**必须改：右栏不得 `display: none`（见 U18）。
- **触达**：任何宽度下，主操作（登录、转世、钱包提取、行囊穿戴 / 卸下、迁跃、查看同场、
  宗门 / 坊市 / 秘境 / 灵宠 / 洞府入口）都必须在至多 2 次操作内到达，且不依赖横向滚动去「找」按钮。
- **可点区域**：全部可点击控件（按钮、chip、图标按钮、行内操作、tab、`<details>` 摘要、
  modal 关闭）命中区 ≥ 44×44 CSS px（视觉可小，命中区用内边距补足；测量以元素边框盒为准）。
- **状态齐全**：`btn-primary` / `btn-soft` / `btn-mini` / `chip` / `btn-icon` / `tab` 六类控件
  必须同时具备 `hover`、`active`、`:disabled`、`loading`（请求中）、`focus-visible` 五态样式；
  现有 `focus-visible` 金色描边保留，不得用 `outline: none` 裸奔。
- **无障碍底线**：关键信息只用文本 + CSS（条、色块均为装饰性补充）；装饰层 `aria-hidden`；
  动态结果（feed、世界消息、modal 打开）沿用现有 `aria-live` / `role="status"` 机制；
  modal 打开时焦点进 modal、Esc / 关闭按钮可关闭（`promptModal` 已有 Esc，推广到聊天 / 奇遇 /
  死亡 modal 的关闭路径——死亡 modal 的「暂不转世」即关闭路径，不得只留 ×）；
  色盲安全：危险 / 警告状态必须同时有文字（血煞、大限将至、冲突区），不得只靠红 / 橙区分。

### 4.2 字段缺口与降级方案（缺口 = 本任务不补后端，只降级）

| 缺口 | 现状证据 | 降级方案（前端必须这样做） |
|---|---|---|
| **G1 寿元总量缺失** | `Lifespan` 有 `birth_base + accumulated_gain`，但 `_status_dict` 只下发 `rem_years`，无总量、无已活岁数 | 寿元只呈现「剩余 X 岁」+ 相对长度条（满槽 100 的现有算法）+ 10 岁大限态；条上不得写百分比、不得写「已用 / 剩余占比」；`rem_years > 100` 时条钳制 100%，数字仍写真实值 |
| **G2 因果刻度缺失** | `sin` / `merit` 无上限、无净值定义 | 不合成善恶条、不算净值、不排高低；只并排双数字 + 血煞标志；道心条单独 0–100，缺失隐藏 |
| **G3 势力主导缺失** | `status` 只有 `sect` / `rank`；`AtlasEngine.dominant_sect(region)` 与区域映射（`WORLD_LOCATIONS[].region`）均不在 `status` 中 | 只呈现归属行；不呈现主导、影响力、折扣徽标；主导查询走已有「版图」按钮的文本结果，不解析文本生成徽标；待后端补字段时另立 Spec 接入 |
| **G4 地点安全缺失** | `status` 无 `is_safe`；现有 `zoneTag` 以「有位置」推断「安全」 | 地点标签只区分三态：闭关（`meditating`）/ 凶域（`conflict_zone`）/ 中性（其余，只写地点名或「—」，不写「安全」）；任何一处不得再出现推断式「安全」文案 |
| **G5 修为分母为字符串** | `exp` 为 `"cur/max"` 字符串，非两个数字字段 | 正则解析失败时只显示原文、不画条、不显示 0%；不得把解析失败写成修为 0 |
| **G6 钱包历史截断** | `wallet_summary` 只取最近 5 条（账本保留 50 条但摘要不下发） | 文案必须写「最近流水（最多 5 条）」；不得写「全部流水」「历史账单」；未知 `kind` 原样显示 `kind` 字符串，不得编造中文映射 |
| **G7 灵气为全局量** | `qi_mult` 来自全局灵气倍率，非角色属性 | 行标签写「全服灵气 ×n」，HUD 同理；不得写成「我的灵气」 |

## §5 可独立验收任务列表（U01–U28；每条独立可测）

> 验收写法统一为：触发界面 / 操作 → 期望呈现 → 数据来源字段 → 降级行为。
> 「字段缺失」指 `status` 中该键为 `null` / `undefined` / 空字符串（空宗门、空职阶按空处理）；
> 降级一律是「隐藏该行 / 该条 / 该徽标并保留其余内容」，不得显示 0、假值或报错。

### 目标 1：整体视觉

- **U01 视觉变量统一**：触发：打开任意主界面卡片（命盘、行囊、钱包、死亡结算、弹层）。
  期望：同一类元素（卡片边框 / 圆角 / 阴影 / 内边距、标题字号与字距、正文 / 次要文字字号）
  全站一致，色板只用 §2.2 的 `:root` 变量。来源：`style.css`（无服务端字段）。
  降级：不适用；实现岗须在报告中列出统一前后的变量对照（删了哪几处散落的硬编码色值 / 字号）。
- **U02 卡片质感与信息密度**：触发：桌面 1440px 与 1100px 下浏览主界面。
  期望：卡片有明确边界与层级（标题金、内容纸白、正文灰），无「白板临时面板」感；
  首屏同时可见命盘关键行 + 天道录 + 至少一组操作按钮，不得为留白把关键信息挤到二屏以下。
  来源：`style.css` 布局。降级：不适用。
- **U03 字体层级**：触发：浏览命盘、日志、弹层、表单。
  期望：标题 / 数值 / 正文 / 次要四档分明，数值带单位（灵石、岁、级、x），
  长文本（日志、世界消息、结算明细）行高 ≥1.6 可读。来源：`style.css`。
  降级：系统字体缺失时按现有回退栈降级，不得下载外部字体、不得出现无衬线标题混衬线正文的断裂。
- **U04 装饰不抢戏**：触发：主界面停留 30 秒；开启系统「减弱动态效果」。
  期望：`.sky` / `.motes` / 金环仅作背景，不遮挡文字与按钮，不随操作闪烁；
  减弱动态下装饰动画停止（现有 `prefers-reduced-motion` 规则保留）。
  来源：`style.css`。降级：不适用。

### 目标 2：关键信息可视化

- **U05 寿元一眼可读**：触发：登录后看 HUD 与命盘寿元行。
  期望：两处同值（`rem_years`，1 位小数 +「岁」）、同色；条为相对长度（`rem_years/100` 钳制），
  条旁必有数字；`lifespan_warning` 或 `rem_years < 10` 时血色 +「大限将至」pill。

### 目标 3：核心流程

- **U11 登录 / 入世流程**：触发：入世页登录与注册。
  期望：登录 / 注册 tab 切换时道号行仅注册时显、主按钮文案同步（登录 / 注册）；
  空用户名、密码 <6 位时 `gateMsg` 就地提示且不发请求；请求中 `btnJoin` disabled +「登录中… / 注册中…」；
  服务端失败时 `gateMsg` 显示服务端错误原文、按钮恢复、已填用户名保留；
  死者登录时不自动建角，直接进死亡结算页（account-death §2.6 已有行为，不得回退）。
  来源：`/register` / `/login` 响应（`dead`、`death_cause`、`legacy`、`wallet`、`settlement`）。
  降级：服地址不可达时 `gateMsg` 显示网络 / 服务端错误原文，不跳转、不清空表单。
- **U12 命盘与钱包行**：触发：命盘钱包盒（余额、户名、流水、提取）。
  期望：户名 + 余额（灵石）+ 最近流水（最多 5 条，`kind` 中文映射与现有 `WALLET_KIND_CN` 一致，
  未知 kind 原样显示）+ 提取表单在同一组内；流水默认收起（`<details>`），展开后可见；
  提取金额非正整数时就地提示不发请求；提取成功后余额以服务端回包刷新并清空输入；
  提取失败时余额不变、错误进 `walletMsg`、输入保留。
  来源：`wallet.{username, balance, entries|ledger[{ts, kind, amount, ref, note}]}`。
  降级：`wallet` 缺失时钱包行与钱包盒显示「—」且提取表单禁用（不是隐藏余额后仍可提交）；
  `entries` / `ledger` 均空时显示「暂无流水。」。
- **U13 行囊流程**：触发：打开行囊卡片；点穿戴 / 服用 / 卸下。
  期望：已穿戴单独成行带「已穿戴」与「卸下」；库存同名合并「×n」带「穿戴 / 服用」；
  阵盘行带「阵盘」；法门行带主修 / 辅修标记；空囊「行囊空空」；件数（`bagCount`）= 库存 + 已穿戴 + 阵盘。
  来源：`inventory`、`equipped`、`arrays`、`skills`、`arts`。
  降级：三数组任一缺失按空数组处理（其余行正常渲染）；操作失败时该行不消失、不错位，
  错误进 feed 错误行。
- **U14 死亡结算与转世引导**：触发：局内死亡、死者登录、会话恢复死者三入口。
  期望：顺序固定（死因与享寿 → 道统与历世 → 资金归集明细 → 寄售待结提示 → 钱包余额与流水 →
  转世三要素指引 → 加成选择 → 新道号 + 转世 / 暂不转世）；转世为主操作最突出；
  加成超 `max_boosts` 时就地提示且不选中；转世失败时 modal 保持打开、道号与加成保留、
  错误进 `deathError`；转世成功后 modal 关闭并在天道录展示转世指引；
  「暂不转世」后给出去向提示且不自动建角；`settlement == null` 时按场景区分文案
  （局内新死「明细未随响应下发」/ 其余「此前已结算」），不得混用、不得捏造明细。
  来源：死亡响应 `sweep` / `settlement`、`death_cause`、`legacy`、`status.wallet`、
  `consignment_open_count`；转世响应 `wallet`、`rem_years`。
  降级：`settlement` 为空时只显示场景文案 + 钱包流水，不补零项明细；
  `consignment_open_count` 缺失时寄售提示写通用文案（留单待售、成交入钱包），不写具体单数。
- **U15 失败提示与防重复提交（全站规则）**：触发：任一按钮 / 表单 / modal 提交后
  （含钱包提取、转世、带参 prompt、聊天、奇遇、心魔选择）。
  期望：请求期间触发控件 disabled + loading 态；二次触发不发请求且有可见提示
  （沿用「天道正在裁决，稍候…」口径，不记为错误）；失败时错误文案出现在触发点附近、
  输入与选择原样保留、页面不跳转、modal 不自动关闭；成功后控件恢复可用。
  来源：`/action` 响应 `ok` / `error`。降级：网络失败时同样适用本条（错误原文进提示区，
  不得只在控制台报错）。
- **U16 带参命令消歧**：触发：点两处「接令」按钮与任一 `data-prompt` 按钮。
  期望：按钮标题 / 弹层标题 / 提示文案写清前置条件（世界页接令：先点「除凶」看凶犯道号；
  坊市区接令：先点「告示」看告示编号——以服务端命令语义为准，文案不得编造新规则）；
  数字类输入（金额、编号）非正整数时弹层内就地提示不发请求；取消 / 点击遮罩关闭后不发请求。
  来源：现有 `data-prompt` / `data-cmd-prefix` / `data-placeholder`（命令本身不变）。
  降级：不适用；命令前缀与占位文案缺失时弹层标题仍须可辨识，不得出现无标题输入框。
- **U17 页签与频道不丢状态**：触发：天道录 / 目标 / 世界三页签切换；世界频道新消息到达。
  期望：切换不清空各页内容；目标类结果进目标页、世间类结果进世界文本区（现有行为保留）；
  世界未读角标只在世界页可见时清零（现有行为保留）；epic / gm 消息 toast 不遮挡主操作按钮。
  来源：`/action` 文本结果、`/world/messages`。降级：频道拉取失败时静默（现有行为保留），
  不弹错、不清已有消息。

## §6 实现与验证指引（给前端岗与测试岗，非 Spec 验收本身）

1. **任务拆分建议**：按验收条目独立提交，每条一个可观察证据——
   视觉（U01–U04）→ 主线可视化（U05–U10）→ 核心流程（U11–U17）→ 移动端（U18–U21）→
   一致性与无障碍（U22–U25）→ 硬约束回归（U26–U28）。不得把多条验收混成一次不可验证的大改。
2. **验证手段**：
   - 静态：`tests/test_qa2_frontend_contract.py`（`status` 键集合）、`tests/test_web_lifecycle.py`、
     与改动模块相关的 pytest；改动前先记基线，失败须标注 `PRE-EXISTING` 还是本次引入。

     对比度工具实测 U23 并记录数值；键盘全流程走查 U25；公网隧道源与本地源各一次走查 U26。
   - 证据：每条 U 须留截图 / 录屏 / 命令输出其一，口头「看过了」不算证据（对照一人公司技能「无证据不称完成」）。

   （规格符合性 / 正确性 / 代码库一致性），must-fix 逐条销账后方可合并；U26–U28 任一失败即驳回。
4. **已知遗留（不由本任务解决，写进报告）**：G1–G3、G5 的后端字段缺口（寿元总量、势力主导、
   修为数字字段）待后端另立 Spec；`season_theme` 除 `name` 外的键、以及 `cave` / `books` /
   `body_soul` 的主视觉提升不在本任务内；两处 `/接令` 的命令语义统一（若需统一）须另立需求，
   本任务只做文案消歧。
