# F10 炼体/炼神双修 Spec

> 上位文档：docs/compose/spec/feature-completion.md（F10）。基线：486a2a4（全量 399 passed，含 F01–F09）。
> 创作者已授权「直接改、无需逐项确认」，本 spec 即阶段一细化结论（requirement-evaluator 五步收敛）。

## 需求本质与核心诉求
- **表层需求**：两条与主境界并行的副修进度——炼体（抗打/寿元微增，资源走妖材）、
  炼神（神识/心魔抗性，资源走悟道类），数值封顶在常量，与主境界并行不喧宾夺主。
- **本质意图**：现有成长只有一条主线（境界修为）。探险掉落的妖兽内丹、灵田产出的百年灵芝
  除卖店/炼丹外缺少长期消耗口；玩家也缺少「不冲境界也能变强一点」的横向构筑选择。
  副修提供低天花板、确定性进度（付资源即升层，无骰子）的横向成长：烧存量材料与灵石，
  换封顶 +10% 战力 / +10 岁寿元 / +20 有效道心，全满也不及一次大境界突破的收益量级。
- **关键目标**：进度落角色新字段（默认值兼容旧档）；双端指令闭环；效果全部接既有判定单点
  （CombatEngine.calculate_power / 突破道心惩罚 / 心魔 death 门 / 神识探查）；
  未修炼时所有因子与旧行为逐字一致（回归基线不破）。

## 现状盘点（实测，2026-11-04）
- **战力**：`CombatEngine.calculate_power` 连乘链：境界基数 × 道心因子（dao_heart/100）
  × 万剑宗门 1.2 × 装备（≤+20%）× 自创神通（≤+20%）× 灵宠（≤+10%）× 心法辅修（≤+6%）。
  各块均为 try 包裹的独立乘子块，F10 照此模式在末尾追加炼体块。
- **寿元**：`Lifespan.add_lifespan(years)` 直接推后 death_timestamp 并累加 accumulated_gain；
  **全仓不存在寿元总量上限（无 MAX_LIFESPAN 类 caps）**——突破增寿 20–40 岁/大境界、
  回春露 +1 岁、事件增寿受 EVENT_EFFECT_CAPS["lifespan_gain"]=15（仅钳 AI 事件提案）约束。
  结论：炼体增寿以「本系统总量封顶」自限（见契约），不依赖不存在的全局 caps；单次 +1 岁
  远低于事件 caps 量级，不构成绕过。
- **道心判定点**（dao_heart 本体 0–100，多处以 max(0, min(100, …)) 钳制写入）：
  ① 突破 `heart_penalty = max(0.0, (80 - dao_heart) * 0.005)`（core/breakthrough.py）；
  ② 心魔结算 death 门：AI 判 death 时 `dao_heart > 20` 则降为 fail（core/heart_demon.py）；
  ③ 斗法 dao_factor、炼丹率等其余读取点本期不动（防涟漪）。
  炼神抗性以「有效道心 = min(100, 本体 + 炼神加值)」只接 ①② 两个抗性判定点，不改本体值、
  不接斗法因子（防与炼体战力叠爆）。
- **神识探查**：`CombatEngine.scan_surroundings` 的 s_sense = tier*100 + sub*25 (+30 天/异灵根)，
  与 c_hide 比出 VAGUE/REALM/FULL 三档清晰度——炼神神识加值接此单点。
- **材料**：妖兽内丹（ITEM_CATALOG material，坊市价 80，探险掉落 ADVENTURE_HERBS、炼丹/委托亦用）、
  百年灵芝（material，价 55，探险掉落/灵田灵芝种子产出）。二者均为既有产出，本期不新造产出点。
- **灵感/阅历计数**：全仓无 inspiration/阅历类持久计数（grep 无果）。故炼神不新造货币，
  改走既有实物材料百年灵芝（其目录 desc 即「温养道基的药材」）+ 灵石，与炼体同构。

## 可行性诊断与系统影响
- **技术可行性**：高。进度是 2 个带默认值的 int 字段；四个效果接入点均为单点单行级改动；
  指令/面板/落库照 F01/F02 双端惯例（引擎只在成功时改角色，handler 成功才 save）。
- **系统影响面**：core/models.py（2 新字段）、core/body_soul.py（新引擎+常量）、
  core/combat.py（calculate_power 末尾炼体块 + scan 神识加值）、core/breakthrough.py（道心惩罚取有效道心）、
  core/heart_demon.py（death 门取有效道心）、server/world.py（4 动作 + 帮助行 + _status_dict 新字段）、
  cli/main.py（4 动作 + 帮助）、web/index.html（修行卡 4 按钮）+ web/app.js（命令 hint）。
  不动表结构、不动既有数值常量、不动 AI 路径。

## 关键设计决策
1. **进度模型：层数制、无经验池**。每执行一次「修炼」付满一层成本即升 1 层（确定性，无骰子）。
   备选「exp 累积制」否决：会引入第二套经验池与半层状态，副修的价值是确定性横向进度，
   成本本身即门槛；层数制下「重复执行刷层」只能靠真金白银的材料/灵石堆满 10 层封顶，不构成刷。
2. **炼神资源：百年灵芝 + 灵石**（非新造灵感计数）。理由见盘点：仓内无灵感计数，
   新造货币违反总纲「不新造产出点/货币」口径；灵芝有探险+灵田双产出，正好给 F06 灵田
   再添一个长期消耗口。炼体同理走妖兽内丹。
3. **效果接入「有效值」模式，不改本体**：炼神只产出 `effective_dao_heart(c)` 供抗性判定点读取，
   karma.dao_heart 本体不被副修污染（事件/心魔对本体的增减口径不变）；斗法 dao_factor 仍读本体。
4. **闭关口径：/炼体 /炼神（含查看）闭关中一律锁门**。与 F02 心法变更、F06 洞府操作的
   防临场刷口径一致（查看与修炼同指令、动作层不可分，整体锁门最简且无绕过面）；
   双端均不进闭关白名单即天然锁门，引擎另对 DEAD 双重拒绝。
5. **修炼不耗时、不占闭关**：副修是即时资源兑换动作（与喂养灵宠同类），不引入新时间轴；
   寿元兑换率由成本表控制（见平衡自检），不存在「挂机刷寿」。
6. **批量参数**：`/炼体 修炼 [n]`、`/炼神 修炼 [n]`，n 默认 1、钳 1–剩余层数；
   逐层校验+扣费，资源中途不足则停在已升层数并报告（≥1 层即 success 并落库），
   首层即不足 → 失败且零扣费零变更。

## 完善后的规则闭环（行为契约）
### 数据（core/models.py，带默认值）
- `body_level: int = 0`（炼体层数 0–10）
- `soul_level: int = 0`（炼神层数 0–10）
- 死亡即旧世消散：新角色字段默认 0，天然闭环，无需死亡钩子。

### 常量（core/body_soul.py）
- `BODY_MAX_LEVEL = 10`、`SOUL_MAX_LEVEL = 10`
- 炼体战力：`BODY_POWER_PER_LEVEL = 0.01`，`BODY_POWER_CAP = 0.10`（满层 ×1.10，与灵宠同量级、全链最小档之一）
- 炼体寿元：`BODY_LIFESPAN_PER_LEVEL = 1.0` 岁，`BODY_LIFESPAN_TOTAL_CAP = 10.0` 岁
  （增寿只在升层瞬间经加值守卫发放：min(单层量, 总封顶 − 层数已发量)，手改脏数据也不能超发）
- 炼神道心：`SOUL_DAO_HEART_PER_LEVEL = 2`，`SOUL_DAO_HEART_CAP = 20`
  （有效道心 = min(100, 本体 + min(20, 2×层数))；对突破惩罚的最大改善 = (80−本体) 段内 20×0.005 = +10% 成功率）
- 炼神神识：`SOUL_SENSE_PER_LEVEL = 3`（满层 +30，恰等于天灵根的探查修正量级）
- 成本（目标层 L，1–10）：材料数 `mat(L) = (L-1)//3 + 1`（L1–3:1、L4–6:2、L7–9:3、L10:4，满层共 22 枚）
  - 炼体：妖兽内丹 × mat(L) + 灵石 `BODY_STONES_PER_LEVEL = 20` × L（满层灵石共 1100）
  - 炼神：百年灵芝 × mat(L) + 灵石 `SOUL_STONES_PER_LEVEL = 15` × L（满层灵石共 825）

### 引擎（core/body_soul.py · BodySoulEngine，照 PetEngine 模式）
- `power_bonus(c)`：1 + min(0.10, 0.01 × body_level)（层数先钳 0–10，脏数据不超发）。
- `sense_bonus(c)`：3 × 钳后 soul_level。
- `dao_heart_bonus(c)` / `effective_dao_heart(c)`：如上契约。
- `next_cost(track, level)`：返回下一层 {item, item_count, stones}，满层返回 None。
- `train_body(c, times=1)` / `train_soul(c, times=1)`：拒绝 死亡 / 已满层；
  逐层「先校验材料数与灵石 → 再扣行囊与灵石 → 升层（炼体同步增寿）」，任一层校验不过即停；
  全程零层成功 → success=False 且角色零变更（材料/灵石/寿元逐项不动）。
- `panel_text(c, track)`：本轨层数/效果/满层状态、下一层成本与库存对照、另一轨一行摘要。

### 效果接入（全部单点、try 包裹或直读引擎纯函数）
- 斗法：calculate_power 在心法槽位块之后追加炼体块连乘（层叠顺序：…× 灵宠 ≤1.10 × 心法辅修 ≤1.06 × **炼体 ≤1.10**）。
  全乘极值约 ×2.02（F02 后）→ ×2.23，炼体一环 +10% 与灵宠同档，不改任何既有环。
- 探查：scan_surroundings 的 s_sense 追加 sense_bonus（只升探查者一侧，不动隐匿侧）。
- 突破：heart_penalty 的 dao_heart 改取 effective_dao_heart。
- 心魔：death 门的 `dao_heart > 20` 改取 effective_dao_heart。

### 指令（server 与 cli 双端一致）
- `/炼体`（body）：炼体面板。`/炼神`（soul）：炼神面板。
- `/炼体 修炼 [n]`、`/炼神 修炼 [n]`：执行修炼。
- 死亡：引擎拒绝 + server 通用口径；闭关：双端均不进白名单（锁门）。

### 状态与网页
- _status_dict 新增 `body_soul: {"body": int, "soul": int}`（纯新增，旧前端忽略）。
- 网页「修行」卡加 4 按钮：炼体（data-cmd=/炼体）、炼体修炼（data-cmd="/炼体 修炼"）、
  炼神、炼神修炼；app.js 命令 hint 补「炼体/炼神」两条。

### 平衡自检（副修总收益必须弱于主修）
- 炼体满层总成本：妖兽内丹 22 枚（坊市价 80 → 等值 1760 灵石）+ 灵石 1100 ≈ **2860 灵石等值**。
  收益：战力 +10%（≈ 一件地品武器 +8% 的量级，但不可叠装备上限外加成另算）+ 寿元 +10 岁。
  对照主修：一次大境界突破增寿 20–40 岁且战力 ×3.5 倍率跃升——副修满层收益显著弱于
  一次破境，符合「不喧宾夺主」。寿元 +10 岁 = 10 现实天，仅够多闭关数日，非永生通道
  （且寿元硬通货总量仍由死亡时间戳决定，副修不改 1 年=1 天的兑换率）。
- 炼神满层总成本：百年灵芝 22 枚（价 55 → 等值 1210）+ 灵石 825 ≈ **2035 灵石等值**。
  收益：突破心魔惩罚至多减免 10% 成功率（且仅当本体道心 <80 时有感）、心魔 death 门槛
  等效放宽 20 点、神识 +30。无直接战力/修为产出，纯抗性与感知，弱于主修。

### AI 边界
零新增 AI 调用；面板文案为本地模板；无 AI 模式完整可玩。

## 潜在不足、盲区与风险（部分已内化进契约）
1. **[材料竞争]** 妖兽内丹同为炼丹/委托/拍卖材料——副修新增消耗口会抬升其需求，
   属预期经济联动（价格锚不变，无印钞面）；灵芝同理（灵田产出可对冲）。
2. **[脏数据超发]** body_level 被手改 >10 时：power/dao/sense 读取一律先钳层数；
   寿元增寿按「已发量 = min(层数,10) × 1.0」守卫，跳层手改不补发历史寿元（只在真实升层瞬间发）。
3. **[批量中途落库]** 批量逐层扣费升层是单次引擎调用内的内存变更，handler 成功才 save；
   进程中途崩溃则整批不落库（材料不丢），可接受。
4. **[CLI/LAN 存档互通]** 同一 CharacterRepository，字段随角色 JSON 走，双端天然一致。
5. **[status 旧前端]** body_soul 为新增字段，旧前端忽略。

## Out of Scope
- 炼体/炼神的独立经验池、失败率/走火入魔、副修功法书/师承。
- 副修与宗门/灵宠/心法槽位的联动加成（各自独立结算，不做组合技）。
- dao_heart 其余读取点（斗法因子、炼丹率、排行榜道行榜）的有效值化。
- NPC 副修（NPC 战力公式不经 calculate_power 的玩家路径，本期不动）。
- 网页独立副修面板页（修行卡按钮 + status 字段即最小闭环）。

## 评审整改（独立 Review 后，2026-11-04）
- 评审结论：可合并、无必须修。5 条建议采纳 4 条：
- **[建议 1] 寿元封顶显式守卫**：升层发放改守卫式——已发量 = 升层前钳后层数 × 单层量，
  本次增量取 min(单层量, 总封顶 − 已发量)，不再只靠 MAX×PER 恒等式。
- **[建议 3] status 口径统一**：_status_dict 的 body_soul 改走 BodySoulEngine 钳后层数，
  与面板/加成同口径（脏数据不报 99 层、非数字不抛错）。
- **[建议 4] 死亡双查**：引擎拒炼条件补 lifespan.is_dead()，与突破引擎口径对齐
  （寿元已到期、status 未结算时亦不可炼体续命）。
- **[建议 5] 测试钉死**：寿元总量/炼神灵石断言补字面值（10.0 岁 / 825 灵石）+ 常量一致性断言；
  死亡用例补行囊/灵石/寿元快照断言。
- **[建议 2] 未采纳（留总纲决策）**：手改存档调低层数后重炼可再得寿元——仓内无任何降低
  body_level 的代码路径，游戏内不可达；彻底堵需新增「已发寿元」持久字段，超出本 spec
  的 2 字段模型，不在本分支自改。
