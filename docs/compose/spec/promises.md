# F14 诺言账闭环 Spec

> 总纲：docs/compose/spec/feature-completion.md · F14
> 路径：requirement-evaluator 五步细化 → 本 spec → worktree 实现 → 全量回归 → 独立评审 → 合并

## 一、需求本质解构

- **表层需求**：补 /许诺 指令——对 NPC/玩家立诺，条件达成自动核验或到期判违约，因果账落账（接 karma_links），履约得功德、违约沾业力并入世情播报。
- **本质诉求**：游戏里已有「恩/仇」因果链（karma_links）与功德/业力账（KarmaLedger），但玩家口头承诺无任何约束与留痕；需要一条「言出法随」的规则闭环：诺言只能由指令立、只能凭既有事实核验、结算只能走既有功德/业力通道，让承诺成为可信的社交资产而非聊天文本。
- **系统定位**：新增 `core/promises.py` 引擎单点 + `promises` 新表；核验钩子挂在四个既有事实落账点（赠礼/迁跃/委托完成/斗法出手）；双端（server/cli）同引擎同口径；网页同场卡加入口。

### 现状盘点（实测结论）

1. **功德/业力唯一账本** = `Character.karma`（KarmaLedger，core/models.py）：`add_merit(v)`（功德 +v 且业力消解 v//2）、`add_sin(v, now)`（业力 +v 且按全仓既有口径沾血煞 3 游戏年）。禁止新造第二套功德数——诺言结算只调用这两个方法。单次 caps 对照 `EVENT_EFFECT_CAPS`：merit 40 / sin 40；既有量级：委托完成 merit +5、除凶 +40~60、杀人 sin +25~40 量级。
2. **karma_links** = `KarmaLink`（core/bounty.py，字段 a/b 双方 + link_type 仇/恩/师徒/宗门 + strength + note），`KarmaLinkRepository` 落账，/因果 面板展示（未知 link_type 默认样式可正常渲染）。诺言结算是「因果账落账」点：终态时写一条 link_type=「诺」的因果链，note 记明践诺/违约与诺目内容。
3. **NPC 态度唯一通道** = `core.npc_mind.shift_attitude(npc, other_id, delta, reason)`（F07 委托完成 +8 先例，内部钳制）。
4. **既有事实点（核验只认这些）**：
   - 赠礼：`core/chat_actions.py::do_gift`（玩家→NPC 会话赠礼，全仓唯一纯赠予结算点；玩家间只有 /交易 出价交换，无纯赠予事实）；
   - 迁跃：server `World._go` 与 cli `/前往` 两处落点后（与 sect_contrib「visit」环钩同位）；
   - 委托整链完成：`QuestEngine.deliver` 完成落账段（与 F09 版图、F11 灵感钩子同段，结构性恰一次）；
   - 斗法出手：`CombatFateEngine.resolve_ambush`（server /斗法、cli /斗法、会话动手三端唯一漏斗；硬前置——安全区/已死/新手庇护/归隐/AI 未就绪——全数拦截后、mark_combat 处，出手即成事实，被拦截的未遂不算出手）。
5. **死亡收尾**：server `World._settle_if_needed` 与 cli `settle_and_reincarnate` 均有 on_owner_death 钩子排（F01 灵宠 / F06 灵田 / F07 委托），诺言同排加入。
6. **世情播报**：`core.jianghu.append_event(kind=..., ...)`（F07/F11 既有口径，尽力而为不炸主流程）。

## 二、行为契约（真正需求）

### 2.1 诺言类型（规则模板池，禁止自由文本判定）

| kind | 指令式 | 对象 | 期限（现实秒） | 核验事实（唯一） |
|---|---|---|---|---|
| gift 赠物 | `/许诺 <NPC名> 赠物 <物品名>` | 仅 NPC | 3 日 = 259200 | 期限内经 do_gift 真赠出同名物品给该 NPC |
| arrive 抵达 | `/许诺 <对象名> 抵达 <地点名>` | NPC/玩家 | 3 日 = 259200 | 期限内迁跃落点 == 目标地点（全名） |
| quest 委托 | `/许诺 <对象名> 委托` | NPC/玩家 | 3 日 = 259200 | 期限内整链委托完成（deliver 完成段） |
| no_attack 不攻 | `/许诺 <对象名> 不攻` | NPC/玩家 | 7 日 = 604800 | 期限内未对该对象出手（出手钩子即时判破）；到期未出手即履约 |

- 地点名子串匹配解析为 WORLD_LOCATIONS 全名（与 /go 同口径），解析不到拒绝立诺；赠物物品名不预检行囊（可先立诺后寻物，与委托寻物环同理），仅要求非空。
- 一人同时未结诺上限 `PROMISE_MAX_OPEN = 3`（PENDING + ACTIVE 合计，按立诺者计）；同一「对象 + 类型」已有未结诺则拒绝重立（防叠诺刷功德）。

### 2.2 成立方式（防单方面陷阱）

- **对 NPC 立诺**：当面（同场）立诺即成立（ACTIVE），NPC 为见证受诺人，天道记账。
- **对玩家立诺**：先入 PENDING（待应诺）；对象在 24 小时（`PROMISE_ACCEPT_TTL_SECONDS = 86400`）内以 `/应诺 [立诺者名]` 应下才转 ACTIVE，**期限自应诺时刻起算**（待应诺不吃期限）；逾期未应 → DISSOLVED（未成之诺，无功无过）。义务只落在立诺者身上，应诺方不承担任何义务——应诺只是「我听见了」，防的是立诺者对不知情者单方面造账。
- 成立条件（双方）：立诺者存活、对象存活、对象与立诺者同场（location 全等）、对象非自己；立诺者处于 DEAD 拒绝。闭关中四指令全部锁门（指令层，见 2.5）。

### 2.3 状态机与结算（幂等）

状态：`PENDING → ACTIVE → KEPT / BROKEN / DISSOLVED`，终态不可逆。`_settle()` 是唯一写终态入口：**先落终态存库（幂等锚），再发效果**（与 F07「先清链后发奖」同构）；已是终态的诺重复触发直接短路，同一诺绝不重复结算。

核验/结算触发点（惰性推进，无新线程）：
- 事实钩子即时结算：赠出命中 → KEPT；抵达命中 → KEPT；委托完成 → KEPT；对受诺人出手 → BROKEN（当场）。
- 惰性结算 `settle_due(char)`：打开 /诺言 面板、/应诺、/毁诺、/许诺 前推进所有涉及 char 的未结诺——待应诺过期 → DISSOLVED；任一方身死 → DISSOLVED；ACTIVE 到期 → 不攻诺 KEPT、其余 BROKEN。
- **一事实践多诺（评审 M1 订正）**：见证人不消费事实——同一次委托完成可同时践多条委托诺（不同见证人），同一次抵达可同时践多条同目标抵达诺；钩子结算全部命中诺而非首条即返。总量受未结上限 3 条约束，功德总量 ≤ 30，不出 caps 量级。赠物诺以受赠人为键、出手以受诺人为键，结构上不可能多命中（同对象同类型防叠）。

结算效果（只走既有通道）：
- KEPT：立诺者 `karma.add_merit(10)`；对象为 NPC 时 `shift_attitude(+8, reason="践诺")`；写 KarmaLink（诺，note=践诺：…）。
- BROKEN：立诺者 `karma.add_sin(15)`（含既有血煞口径）；对象为 NPC 时 `shift_attitude(-8, reason="背诺")`；写 KarmaLink（诺，note=违约：…）；`jianghu.append_event(kind="promise")` 世情播报。
- DISSOLVED：无任何效果、不写因果链、不播报。

效果落账的活对象原则（F05 教训）：结算时若调用方持有立诺者活对象（如斗法中的 attacker），优先在该对象上原地落账并回存，防调用方随后以旧对象回存覆盖；否则仓储新鲜加载 + 回存。钩子返回的结算文案由宿主流程呈现（赠礼文本/迁跃文本/交付消息/斗法战报）。

### 2.4 毁诺

`/毁诺 [受诺人名]`：ACTIVE 诺主动毁弃 = 自认违约，与逾期违约**同额同罪**走同一 _settle(BROKEN)（业力 +15、态度、因果链、世情播报俱全）——毁诺后诺已终态，随后再动手不重复判，也不比等到期更便宜，无空子可钻。PENDING 诺毁弃 = 应诺前撤回 → DISSOLVED 无代价（诺未成）。多条未结诺时须指明受诺人。

### 2.5 指令面（双端一致）

| 指令 | 别名 | 行为 |
|---|---|---|
| `/许诺 <对象名> <诺目> [参数]` | /promise | 立诺；无参/参数不足给用法（含「交谈口头应承不算」提示） |
| `/应诺 [立诺者名]` | /acceptpromise | 应下待应诺；多条时须指名 |
| `/诺言` | /promises | 先 settle_due 再展示面板（我立之诺/待我应诺/我受之诺/近史） |
| `/毁诺 [受诺人名]` | /breakpromise | 见 2.4 |

- 死亡口径：立诺者 DEAD 时引擎拒绝（四指令同 F07 社交/行动类口径）；对象 DEAD 在立诺与惰性两处校验。
- 闭关口径：四指令**均不进** server 闭关白名单（med_ok）、CLI 同步锁门——立诺/应诺/毁诺是当面社交行为，面板亦随同类锁门（与 F07 四指令一致，测试逐条断言）。
- 网页：同场修士卡加「诺言账」（data-cmd=/诺言）、「许诺…」（data-prompt + data-cmd-prefix=/许诺）、「应诺」（data-cmd=/应诺）按钮，零前端逻辑。
- 目标解析：按名精确查（CharacterRepository.get_by_name，与 /斗法 同口径）；同场与存活由引擎统一校验，双端不另设口径。

### 2.6 AI 边界

- 立诺/核验/结算零 AI 调用，引擎无 AI import。
- 交谈（含 AI 分类/应答）中出现的「我答应你」等文本**不产生任何诺言行**；帮助文案与面板首行明示此口径，防玩家误解（有真实会话路径测试断言零诺行）。

## 三、不足与盲区扫描（五步之四）

1. **[陈旧对象覆盖]** 斗法结算中钩子若另加载立诺者副本落账，调用方随后 save 活对象会覆盖——以活对象优先原则化解（2.3）。
2. **[未遂误判]** 安全区/庇护拦截的出手不算违约——钩子置于硬前置全过后，拦截路径不触发（有测试）。
3. **[诺后反悔钻空]** 先毁诺再动手：毁诺已同额结算且诺已终态，动手不重复判、总代价不低于直接违约（2.4）。
4. **[叠诺刷功德]** 同对象同类型防叠 + 未结上限 3 + 一事实践多诺总量 ≤ 30 功德；每次践诺都要求一条真实事实链（真赠物/真办委托/真迁跃），成本真实。
5. **[对象离线]** 玩家对象立诺只要求同场存活，不查在线会话；PENDING 24 小时不应即消散，不会永久占名额。
6. **[赠物全名口径]** 赠礼匹配是行囊子串模糊命中，诺言核验以物品**全名同字**为准；立诺时若行囊已有含参物品则将诺面参数规范为全名，并在立诺消息中明示全名口径（评审 S2）。
7. **[名额占用]** make_promise 先 settle_due 再算上限/去重，过期诺不长期占名额（评审 S3）。
8. **[数据量]** 诺行按 char 关联过滤、全表扫描在当前规模可接受（评审 S6 记录，规模化后再加索引查询）。

## 四、验收标准

- tests/test_promises.py 覆盖：常量 caps、立诺成立条件（同场/对象存活/赠物仅 NPC/地点解析/已在目标地）、上限与防叠、玩家 PENDING→应诺→ACTIVE（期限自应诺起算）与不应消散、多待应须指名、四类事实核验真实路径（do_gift 真赠/错赠/迟赠、deliver 整链完成、note_arrival 与 server /go、resolve_ambush 真斗法/安全区未遂/诺期已满后出手）、一事实践多诺（M1 回归）、到期违约数值与播报、结算幂等（重复推进/迟到钩子/因果链恰 1 条）、毁诺双路径、死亡双向消散、交谈不立诺、面板与旧档兼容、server handle 全流 + 闭关锁门、CLI 源码对齐。
- 全量回归 0 失败（基线 464 + 新增）。
- 独立评审必须修项整改后复跑全量并复验。

## 五、Out of Scope（明确不做）

- 玩家间赠物诺（无纯赠予事实点；玩家间走 /交易）；诺言转让/连环诺/组队诺。
- 以灵石/物品作诺押金托管；违约自动赔付（只记 karma 账）。
- NPC 主动向玩家立诺、NPC 之间诺言（江湖模拟不接）。
- 诺言排行榜、声望（prestige）联动（F11 声望字段后续自取）。
- 自由文本诺目与 AI 判定履约（明确禁止，防幻觉造账）。
