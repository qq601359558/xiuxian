## §0 五步推演结论（简明）

### 0.1 需求本质解构

- **表层需求**：修两个已由 Martinez 拍板的截图缺陷——(1) 注册进入后中央舞台首屏一大块空黑板；
(2) 390px 手机首屏命盘与行囊并排、行囊被挤到只露一半。
- **本质意图**：两者都不是「缺内容/缺样式」，而是**状态与布局契约被破坏**：
(1) 日志数据完整写入 DOM，却因页签状态被入世前的无关点击清零而整体不可见——
玩家第一眼以为游戏没加载，直接动摇「能玩」的信任；
(2) ≤780px 布局把左栏设计成横向条带，与卡片的自然宽度、舞台的高度预算互相打架，
首屏既看不全行囊、也几乎看不见舞台。
- **系统定位**：纯表现层。数据流（`/register` `/login` `/action` 响应、`#log` 写入路径、
`applyStatus` 渲染）均正常，已由对照实验排除（见 §2.1 证据 5）。

### 0.2 可行性评估

- **技术可行性：高**。缺陷 1 是事件绑定作用域 + 页签切换健壮性问题，缺陷 2 是单个媒体查询内的
布局规则问题；均在 `web/` 内闭环，无新依赖、无接口变更。
- **成本**：小。但两处都属「一行改错、全站回退」的位置（全局 `.tab` 选择器、≤780px 布局），
必须按本 Spec 的不变量与回归项验收，不得顺手重构。

### 0.3 不足与盲区（推演中发现）

1. 缺陷 1 的触发点在**登录前**（点「注册」页签），修复若只写在入世流程里（如入世时强制切回
天道录），是症状修复：页签不变量在登录前已被破坏、且任何未来调用方传入非法页签名仍可
把舞台整体熄灭。必须修根因（见 §3.1 备选取舍）。
2. 缺陷 2 若只把左栏改成纵向堆叠而不给高度预算，左栏四卡自然高度合计远超视口，
会把舞台再次挤出首屏（`body{overflow:hidden}` 下甚至不可达）——「单列」与「舞台首屏可见」
必须同时进契约（见 §1 F2 契约与 §3.2）。
3. 同族风险：`web/app.js` 中按 `.tab` 全局选元素的绑定不止一处（打开世界页清角标的绑定同理），
修复时须一并核查作用域，但**不得**顺带改动其行为语义。

### 0.4 举一反三

- **横向**：凡「同名 class 跨区域复用」（入世区页签 vs 舞台页签）都是同类雷区；本轮以
「页签不变量」（§1 契约 C-1）把这类问题一次性钉死，而不是只修本次触发路径。
- **纵向**：≤780px 左栏改为纵向后，未来左栏新增卡片只会加长左栏内部滚动，不再影响舞台与
横向布局；右栏抽屉的既有单列规则与之口径一致，布局心智统一。
- **涟漪**：页签切换被 `send()`、目标结果回填、世界消息轮询（史诗/天道消息自动切世界页）等
多处复用，任何改动必须保证这些既有调用的落点不变（见 §5 R 类回归）。

### 0.5 完善方案

- 推荐路径：缺陷 1 = 「绑定作用域收敛 + 页签切换非法值无操作」双保险（§3.1 方案 A）；
缺陷 2 = 「≤780px 左栏纵向单列 + 高度有界、栏内纵向滚动」（§3.2 方案 A）。
- 真正需求与验收以 §1、§4 为唯一依据。

## §1 真正需求条目与行为契约

### 全局不变量

- **C-1（页签不变量）**：任意时刻，舞台三个 pane（`#pane-feed` / `#pane-goals` / `#pane-world`）
中**恰有一个**带 `active`；舞台三个页签（`data-tab="feed"|"goals"|"world"`）中恰有一个带
`active`，且二者对应。此不变量在页面加载后、登录前、登录/注册后、任意页签点击后、
任意指令执行后均须成立。
- **C-2（入世区与舞台隔离）**：入世区「登录/注册」切换只改变认证模式（按钮文案、道号字段显隐），
不得改变任何 pane / 舞台页签的 `active` 状态。
- **C-3（存储与标识零变更）**：不改任何 DOM id、不改 `localStorage` 键（`td_base`/`td_token`/
`td_name`/`td_uid`/`td_user`）、不改接口路径与请求/响应字段。

### F1 — 主舞台首屏空白（缺陷 1）

- **问题**：新用户注册（必经点击「注册」页签）进入游戏后，舞台区为整块空面板；
注册成功/寿元/初入道三行日志实际已写入 `#log`，但不可见。玩家发出第一条指令或点任意
舞台页签后才「自愈」，故极易被误判为加载失败。
- **行为契约**：
1. 注册、登录、会话恢复三条入世路径完成后，默认落点均为天道录（feed）且日志立即可见
（除非该路径本身已有既定落点，如目标结果回填切目标页——保持现状）。
2. 页签切换逻辑收到空值、未知值或不对应任何 pane 的值时，必须**无操作**（保持当前
active 不变），不得把全部 pane 熄灭。
3. 舞台页签的点击处理只应作用于舞台页签本身；入世区页签不得触发舞台页签逻辑
（含清角标等附带处理）。
4. 既有合法切换行为不变：点目标页签、目标类结果、世界史诗消息自动切世界页、
`send()` 回天道录等（见 §5 R-1～R-3）。

### F2 — 手机首屏行囊被挤（缺陷 2）

- **问题**：390px 下左栏被排成横向条带：命盘卡 260px + 行囊卡 240px 并排，行囊右半截
在视口外（实测右缘 520px > 视口 390px），「法门：吐纳术、御剑术」一行在屏幕边缘被截断；
同时舞台被该条带挤到首屏之外（实测舞台高仅 2px）。
- **行为契约**（仅 ≤780px；>780px 布局一律不变）：
1. 左栏四卡（命盘/行囊/修行/迁跃）**纵向单列、全宽**排列：每张卡片左缘 ≥ 壳层左内边距、
右缘 ≤ 视口宽，卡内文字按卡宽自然换行，不得被视口截断。
2. 左栏区域**无横向滚动**：左栏 `scrollWidth ≤ clientWidth`，页面无横向滚动条。
3. 左栏高度**有界**：左栏占壳层高度不得使舞台失去可用高度——390×844 下舞台在首屏内
可见且高度 ≥ 240px；左栏超出部分以**栏内纵向滚动**到达（修行/迁跃卡可经滚动完整查看
并点击），不得靠页面滚动（`body` 仍 `overflow:hidden` 的既有约定不变）。
4. 行囊内容口径不变：行囊空态、「法门：…」行、已穿戴/阵盘行均按现有渲染呈现，只改容器布局。

## §2 确诊成因（附代码证据）

> 实证方法：在 `/tmp` 放 worktree 代码副本（全新 DB），游戏服 8765 + 静态托管 8080
> （起服带 `no_proxy/NO_PROXY=localhost,127.0.0.1`），用 `~/workspace/tools/ui-shot/` 的
> Puppeteer 无头 Chromium 注册新角色「观澜」复现，并量测 DOM 几何与计算样式；
> 另设对照组（不点入世区页签、经 API 预注册后纯登录）。worktree 与主仓未起服、未写 data。

### 2.1 缺陷 1：入世区页签与舞台页签共用 `.tab`，点「注册」把三个 pane 全部熄灭

**一句话结论**：日志没丢、没被滚出、没渲染错地方——是登录前点击「注册」触发了舞台的
页签切换处理（传入的页签名为空），把 `#pane-feed` 的 `active` 摘掉且无任何 pane 接替，
日志行随 `display:none` 的父容器整体不可见。

证据链：

1. **同名 class 跨区复用**：入世区页签 `<button class="tab" id="tabLogin">` /
`<button class="tab" id="tabReg">`（`web/index.html:65-67`）**没有 `data-tab` 属性**；
舞台页签同用 `class="tab"` 但带 `data-tab="feed"|"goals"|"world"`
（`web/index.html:256-258`）。日志本体在 `#pane-feed.pane.active > #log`
（`web/index.html:265-266`），初始 HTML 中 feed 是唯一 active，初始状态正确。
2. **全局绑定误伤**：舞台页签点击绑定用 `document.querySelectorAll(".tab")` 无作用域地
选中**全部** `.tab`（含入世区两个），点击即调用页签切换并传入
`tab.getAttribute("data-tab")`（`web/app.js:1571-1578`）；入世区页签的该值为 `null`。
3. **切换函数不设防**：页签切换按「页签 `data-tab === name`、pane `id === "pane-" + name`」
重排全部 `active`（`web/app.js:560-567`）。`name=null` 时 pane 匹配 `"pane-null"` 无一命中
→ 三个 pane 全部失去 `active`；而 `.pane{display:none}`、仅 `.pane.active{display:flex}`
（`web/style.css:693-699`），舞台内容区随之整体隐藏。同一调用还把两个入世区页签同时
点亮（`null===null` 均判真）——实测点击后 `#tabLogin` 与 `#tabReg` 同时带 `active`，
是误伤的指纹（其后认证流程末尾重设认证模式才把入世区页签外观修正，故截图上不显眼）。
4. **入世流程不恢复、日志照常写入隐藏容器**：注册成功后入世处理只切换入世区/主界面的
显隐并依次写三行日志（`web/app.js:1339` 起 `enterWorld`，日志写入在其函数体内），
随后全量刷新（`web/app.js:1452` 的 `refreshSoft(true)`）只更新命盘/同场，不触碰页签状态；
日志写入函数把行追加到 `#log` 并设滚动位置（`web/app.js:37-47`），在高度为 0 的隐藏
容器上执行无异常、无可见效果。
5. **实测量测（与截图严丝合缝）**：注册路径下 `.panes` 容器本身尺寸正常（842×728，
即截图中的空黑板），但三个 pane 计算样式均为 `display:none`，`#log` 与其 2～3 个
`.line` 子元素几何均为 0×0，`innerText` 却能完整读出「观澜 · 练气期初期 /
自然寿元约 … 岁 · 道统池 0 点 /三步：…」——正是「DOM 里有、截图上没有」。
**对照组**：经 API 预注册、UI 上不点任何入世区页签直接登录，`#pane-feed` 保持
`active`，`#log` 为 842×728、首行 806×24 正常可见——排除日志渲染、颜色、滚动定位、
渲染时机四类嫌疑（日志行颜色/字号计算值均正常，内容量仅 3 行不存在滚出可视区）。
6. **为何「用一会儿就好了」**：任一舞台页签点击、或发出任意指令（发送路径会切回
feed，`web/app.js:638`）都会重新点亮一个 pane——实测在熄灭态点「天道录」后
`#log` 立即恢复 842×728 且原有日志行全数显现（未丢失）。故本缺陷只伤首屏第一印象，
且专伤**新注册用户**（注册必点「注册」页签；老用户纯登录不触发）。

附带同族点：世界角标清零的点击绑定同样以 `.tab` 全局选取元素（`web/app.js:1805` 起），
当前因其内部只处理 `data-tab="world"` 而无实际危害，但与缺陷同源，修复时须同批收敛
作用域（行为语义不变）。

### 2.2 缺陷 2：≤780px 左栏被设为横向条带 + 卡片 240/260px 最小宽，竖排右栏反而有单列规则

**一句话结论**：≤780px 媒体查询把左栏改成横向 flex 条带并给卡片设了 240px（命盘 260px）
最小宽，四卡总宽 1010px 塞进 370px 壳层只能横向溢出，行囊卡右半截落在视口外被截断；
同批规则只给**右栏抽屉**写了窄屏单列覆盖、没给左栏写，所以「打开场景面板后单列」的是
右栏而非左栏。

证据链：

1. **横向条带规则**：`@media (max-width:780px)` 内 `.rail.left{flex-direction:row;
overflow-x:auto; overflow-y:hidden}`（`web/style.css:1118` 起，左栏规则在 1125-1130），
`.rail.left.card{min-width:240px}`、`.rail.left.card.fate{min-width:260px}`
（`web/style.css:1131-1132`）。同区 `.shell` 改为单列网格
`grid-template-columns:1fr; grid-template-rows:auto minmax(0,1fr)`（`web/style.css:1120-1123`）。
2. **实测量测（390×844，会话恢复进入）**：壳层宽 370px；左栏四卡左/右缘依次为
命盘 10→270（宽 260）、行囊 280→**520**（宽 240，右缘超出视口 130px，首屏仅露约 110px）、
修行 530→770、迁跃 780→1020；左栏 `scrollWidth=1010 > clientWidth=370`。
行囊「法门：吐纳术、御剑术」（`web/app.js` `renderBag` 写入 `#bagArts` 的纯文本行）
本身按卡宽换行，截断点恰在视口右缘——是**卡片被视口切掉**，不是文本溢出样式问题。
3. **连带挤压舞台**：网格首行 `auto` 由左栏条带高度决定（实测左栏高 550px，占壳层 584px
的绝大部分——横向排列时卡高被条带交叉轴拉伸至等高），次行舞台实测高仅 **2px**
（y 834→836），即 390px 下舞台同样不在首屏内。此为本缺陷的组成部分（与缺陷 1 机制
独立：桌面端舞台尺寸正常，见 §2.1 证据 5）。
4. **「打开场景面板后恢复单列」的真相**：点 `#railToggle` 仅给 `.shell` 加 `rail-open`
类（`web/app.js:1592-1600` 的绑定）。实测 toggle 后左栏四卡坐标**逐像素不变**
（仍 10→270 / 280→520 / …），左栏并未恢复单列；变化的是右栏：≤1100px 规则令
`.shell.rail-open.rail.right` 显示并横排（`web/style.css:1107-1114`），而 ≤780px 另有
覆盖 `.shell.rail-open.rail.right{flex-direction:column; flex-wrap:nowrap}` +
`.card{flex:1 1 auto}`（`web/style.css:1137-1138`），故**右栏**（此地/同场诸卡）落成
全宽单列——此前口头描述的「恢复单列」实为右栏现象，不能作为左栏已修的依据；
本轮验收以左栏自身量测为准（F2-x）。

## §3 Design（定行为与样式契约，不绑架私有函数名）

### 3.1 缺陷 1 修复设计

改动点（`web/app.js` 为主；如需动 `index.html` 仅限不改 id、不改既有 class 语义的范围内）：

1. **绑定作用域收敛**：舞台页签的点击处理只绑定舞台页签集合——判据是「带合法
`data-tab`（feed/goals/world）」或「位于舞台页签容器内」，二选一，实现者自选；
入世区页签点击后，除认证模式变化外，DOM 中任何 pane / 舞台页签的 class 不得变化。
世界角标清零绑定同批按同一口径收敛（语义不变）。
2. **切换健壮性（纵深防御）**：页签切换入口对名称做白名单校验——名称不属于
{feed, goals, world} 时直接返回、无任何 DOM 变更。与第 1 点同时落地，缺一不可：
只做 1 是「当前触发点消失、雷还在」，只做 2 是「雷被挡住、但入世区页签仍在
无意义地调用舞台逻辑」。
3. **不新增恢复逻辑**：不在入世流程里补「强制切 feed」作为修复手段（可保留其现有
行为，但不得以它代替 1+2）；修复后注册路径天然满足 C-1。

备选与取舍：

| 方案 | 内容 | 取舍 |
|---|---|---|
| **A（推荐）** | 作用域收敛 + 非法值无操作（上述 1+2） | 根因修复，改动面最小，不变量可测 |
| B | 仅给入世区页签改名/换 class | 须连带改 CSS 两套页签样式与认证模式切换逻辑，churn 大且仍留「非法值熄灭舞台」的函数级雷区，弃 |
| C | 仅在入世完成时强制激活 feed | 症状修复：登录前不变量已破、死者登录/会话恢复等其他路径继续带雷，弃（可作 A 之外的额外保险，但不计入验收依据） |

### 3.2 缺陷 2 修复设计

改动点（仅 `web/style.css` 的 `@media (max-width:780px)` 段；如确需亦可微调同段内
`.shell` 行定义，不动 780px 以上任何规则）：

1. **左栏改纵向单列**：≤780px 时 `.rail.left` 为纵向排列（`flex-direction:column`），
卡片最小宽约束解除（`min-width:0` 或等效），卡片宽度随壳层全宽（扣除壳层内边距），
左栏 `overflow-x` 不再产生横向滚动。
2. **高度有界 + 栏内滚动**：左栏在其网格行内 `min-height:0` 且可纵向滚动
（`overflow-y:auto`），网格首行高度须有上限口径，使 390×844 下舞台高度 ≥240px 且
位于首屏（具体实现——固定比例、最大高度或行高组合——由实现者定，以 F2-3 量测为准；
不得用页面级滚动解决，`body{overflow:hidden}` 不动）。
3. **右栏抽屉口径不变**：`.rail-open` 右栏在 ≤780px 的既有单列规则（1137-1138）原样保留；
左栏新规不得与之互相覆盖出第三种形态。≥781px 的左栏（默认纵向列）与 ≤1100px 的
两栏布局均不得受影响。

备选与取舍：

| 方案 | 内容 | 取舍 |
|---|---|---|
| **A（推荐）** | 纵向单列 + 高度有界 + 栏内纵滚（上述 1+2） | 与右栏单列口径统一；行囊全宽可读；舞台回首屏 |
| B | 保留横排，改卡宽为整卡宽 + 滚动吸附（scroll-snap） | 行囊仍须横滑才见全卡，与「落回单列」的既定预期不符，且舞台被挤出首屏的问题依旧，弃 |
| C | 左栏改折叠/手风琴（如行囊默认收起） | 交互与信息层级变更超出本轮授权（只修缺陷），弃；如未来需要另立 Spec |

## §4 编号验收项（每条带可复现检查方法）

> 通用检查环境：隔离副本（全新 DB）起服（游戏服 8765、静态 8080、`no_proxy` 同 §2），
> Puppeteer 无头 Chromium；桌面视口 1440×900、手机视口 390×844（isMobile）。
> 「量测」指 `getBoundingClientRect()` / 计算样式 / `scrollWidth` 等 DOM 量测，
> 截图仅作辅助留档，不作唯一判据。

### F1 类（缺陷 1）

- **F1-1 注册首屏日志可见**：全新 DB，UI 上点「注册」页签→填新账号→注册进入。
判据：`#pane-feed` 带 `active` 且计算 `display:flex`；`#log` 高度 > 600px（1440×900 下
基线 728px）；`#log` 内含「」「自然寿元约」「」三行且首行
几何高度 ≥ 20px；桌面截图舞台区可见该三行文字（非空黑板）。
- **F1-2 纯登录不回退**：同 F1-1 账号退出后，不点任何入世区页签直接登录。
判据同 F1-1（日志含「」或「」且可见）。
- **F1-3 入世区点击不污染舞台（登录前）**：在入世页依次点「注册」「登录」「注册」。
判据：每次点击后三个 pane 的 class 与初始完全一致（feed 唯一 active），
舞台三页签 class 不变；入世区两页签恰一个 `active`（与当前认证模式一致）。
- **F1-4 非法页签名无操作**：进入游戏后，在控制台以现有页签切换入口分别传
空值与未知值（如 `""`、`"null"`、`"settings"`）触发（若实现已无可达的非法入口，
则以代码审查 + F1-3 代替本条动态触发，并在报告中注明）。
判据：触发前后 C-1 不变量成立，当前 active pane 不变，`#log` 内容不丢。
- **F1-5 自愈路径不依赖**：注册进入后**不做任何点击/指令**、静置 ≥ 6 秒（跨一个
5 秒轮询周期）。判据：日志仍可见（轮询刷新不得把 pane 状态改坏），同 F1-1。

### F2 类（缺陷 2）

- **F2-1 行囊卡全宽单列**：390×844 进入游戏（注册或会话恢复均可）。
判据：左栏四卡纵向排列（后一卡 `top` ≥ 前一卡 `top`、同列左缘对齐，允许栏内滚动后
量测布局序）；行囊卡右缘 ≤ 390 且左缘 ≥ 10（壳层内边距）；「法门：吐纳术、御剑术」
一行完整可见于截图（文字可在卡内换行，但不得被视口右缘截断）。
- **F2-2 无横向滚动**：同 F2-1 状态。判据：左栏 `scrollWidth ≤ clientWidth + 1`；
`document.scrollingElement.scrollWidth ≤ 390`；页面无横向滚动条。
- **F2-3 舞台回首屏且可用**：同 F2-1 状态、左栏未滚动前。判据：舞台（`.stage`）
`top < 844` 且高度 ≥ 240px；舞台内天道录日志区可见（与 F1 修复叠加后应见入世日志）。
- **F2-4 左栏纵滚可达**：同 F2-1 状态，将左栏滚动到底。判据：迁跃卡完整进入左栏
可视区（其矩形在左栏矩形内），其任一迁跃按钮可点击且点击后发出对应指令
（日志新增一行或地点变化，二者其一即可）。
- **F2-5 场景面板行为不变**：同 F2-1 状态点「场景面板」。判据：右栏以全宽单列出现
（其卡片右缘 ≤ 390），再点一次收起；开关前后左栏四卡的布局形态（单列/宽度）不变。

### R 类（回归）

- **R-1 舞台页签切换全量**：桌面端依次点「目标」「世界」「天道录」。
判据：每次恰一个 pane active 且与页签对应；点「目标」仍触发既有目标拉取、
世界页角标清零行为不变。
- **R-2 指令与结果回填**：桌面端执行一条普通指令（如点「观照」）与一条目标类指令。
判据：普通指令后回天道录且日志新增「» …」与结果行；目标类结果仍按既有规则
回填目标页（行为与基线一致，逐项对照 `1e2ef9d` 行为）。
- **R-3 世界消息自动切页**：触发或等待一条 epic/gm 级世界消息（或以既有测试手段
注入）。判据：仍自动切到世界页且 toast 出现；切页后 C-1 成立（world 唯一 active）。
- **R-4 布局断点不回退**：分别在 1440、1100、781、780、390 五个宽度量测。
判据：1440 为三栏（左 260/右 280 基线口径）、1100 与 781 为两栏 + 右栏抽屉行为不变、
780 起左栏单列生效、390 满足 F2 类；1100 宽度下 HUD 寿元/修为宽格保留。
- **R-5 既有测试套件**：跑 `tests/test_qa2_frontend_contract.py` 及与 web 相关的
既有测试（至少含 `tests/test_web_lifecycle.py`），全绿；全量回归口径与基线
`1e2ef9d` 对比无新增失败（基线 674 passed，PRE-EXISTING 失败须标注）。
- **R-6 标识零变更审查**：diff 审查。判据：未改任何 DOM id、`td_*` 存储键、接口
路径/字段；改动文件仅 `web/` 内文件（及按流程更新的本 Spec 状态/报告）。

## §5 风险与涟漪

1. **页签切换是多方复用入口**：发送指令（回 feed）、目标结果回填（切 goals）、
世界轮询（epic/gm 切 world）、世界角标清零均与 `.tab`/`active` 机制耦合（§2.1）。
作用域收敛时若误伤舞台页签本身的绑定，将表现为「页签点了没反应」——R-1/R-3 必须实测，
不能只测注册路径。
2. **认证模式切换与页签 class 的历史纠缠**：入世区页签的外观 active 此前同时被两套
逻辑改写（认证模式切换 + 被误绑的舞台切换）。收敛后须确认入世区页签外观只由认证
模式决定（F1-3），且「登录/注册」文案、道号字段显隐、提交路径（`/login` vs
`/register`）不变。
3. **死者登录与会话恢复路径**：这两条路径同样写日志/弹死亡页且不走完整入世流程；
C-1 不变量修复后应顺带受益，但须抽查死者登录一次（死亡弹层出现、日志行可见），
避免修复只覆盖注册一条路径（并入 F1-5 的抽查项由实现报告注明）。
4. **≤780px 高度预算的连锁**：左栏改纵向后，若高度上限口径过松，舞台被挤出首屏
（缺陷 2 的连带项复发）；过紧则命盘关键行（寿元/钱包）需滚动才见。F2-3 的 240px
是下限判据而非目标值；实现报告应给出 390×844 与 390×667（矮屏）两组量测。
5. **断点边界**：780/781 与 1100/1101 两组边界两侧布局不得同时命中两套规则或都不命中
（R-4 逐点量测）；右栏抽屉在 781–1100 的横排形态不得被左栏新规污染。
6. **禁止顺手扩大**：HUD 在手机端换行占高（实测约 250px）、桌面钱包盒在首屏下方等
现象是既知问题但不在本轮范围（见 §6），实现中不得顺带调整，以免验收口径漂移。

## §6 Out of Scope（明确不做）

- **游戏规则与数值**：任何 `core/` / `server/` 改动、寿元/因果/势力等规则语义。
- **API 契约**：接口路径、请求/响应字段、错误口径一律不变；前端不得新增字段依赖
（`tests/test_qa2_frontend_contract.py` 的字段子集约束继续有效）。
- **DOM id 与存储键**：既有 id（`#log`、`#pane-*`、`#tabLogin`、`#tabReg`、`#railToggle` 等）
与 `td_*` 存储键不改名、不增删语义。
- **第三个毛病「桌面钱包在首屏下方要滚动」本轮默认不修**：左栏命盘卡内容长、钱包盒
位于卡内末尾，桌面端需滚动左栏才见——本轮不调其位置/顺序/折叠形态；如 Martinez
另行拍板，另立 Spec。
- **手机端 HUD 占高优化**：HUD 在 ≤780px 换行至约 250px 高，本轮不压缩、不折叠。
- **日志系统改造**：日志行数上限（400）、着色分类、滚动跟随策略均保持现状；
本轮不做「空舞台引导块」类新增 UI（缺陷 1 的根因不在缺引导）。
- **入世区视觉改版**：入世区页签不换名、不换样式体系（方案 B 已弃）；仅允许其
事件作用域被隔离。
