## §0 · 五步推演结论摘要（requirement-evaluator）与代码事实纠正

### 0.1 五步推演

**第一步 · 解构本质。** 表层需求是「再修几个 undefined」——宝图面板「攻伐 +undefined」修完后，Martinez 的判断是游戏「存在很多漏洞，还没达到可用状态」；本质是**前后端契约无全量对账**：服务端返回什么形状、前端按什么形状渲染，两边从来没有一张逐项对过的台账，单个 bug 的修复只能证明修过的那一个点没问题，证明不了其余 193 个分发分支、509 行 `_status_dict`、三端渲染面都没有同类问题。验收本质因此不是「又修了 N 个 bug」，而是三件可复核的交付物：① 一张**全量台账**（每个消费面一行，结论逐项可复核）；② 台账中每一项的处置（修复或定性不修的理由）；③ 一层**防复发契约**（测试资产），使下一轮发版能自动复检同一类口径。缺其中任何一件，本轮都没有兑现「先扫清同类不一致再汇报」的承诺——N 的大小本身不是验收标准，台账的完整性才是。

**第二步 · 可行性评估。** 可行，方法是枚举 + 双向差集 + 真实响应抓取（三者缺一不可，见 §2）。成本画像（实测，§0.2）：前端三文件 workbench.js 7898 行 / app.js 2462 行 / mobile.js 1645 行；服务端入口 `server/world.py` 的 `/命令` 分发约 193 个分支 + `_status_dict` 509 行（:4551–5060）+ 登录/入局/转世/死亡等 payload 出口；另有 CLI（`cli/main.py` + `cli/views.py`）文本渲染面。工作量大头在枚举与逐项对照（机械但量大），不在单个修复（单个修复多为渲染口径或只增字段的小改）。移动端预算：mobile.js 现 1645 行，现行上限 1892 行余 247 行、mobile.css 27395B（上限 28800B）余 1405B——但**三期硬线测试仍把 mobile.js 卡在 ≤1660 行（只剩 15 行，§0.2-F5）**，本轮移动端新增以硬线为准，超硬线即停工回主策岗。性能开销：审计本身零运行时开销；契约测试只在测试期跑真实响应抓取与静态扫描，不进生产路径；修复只改渲染口径与只增字段，不动结算本体，响应耗时不劣化（验收 RG 组以基线对照）。

**第三步 · 不足与盲区（均已在方法论中堵住，标注落点）。**
1. 枚举遗漏是本轮最大的失败模式：只扫 `res.xxx` 会漏掉别名（`state.status`/`s.`/`data.`）、模板插值、通用渲染（`Object.entries`）与动态键——§2.1 先定「别名清册 + grep 模式清单」，再枚举消费点，漏一类即台账不完整。
2. 服务端同一字段在不同分支形状不同：同一键名在 A 分支是数字、在 B 分支是字符串/缺失（例如 `stone_gain` 在 brute_force 分支根本不存在、由 `res.get("stone_gain", 0)` 补 0，见 §0.2-F2）；按「键名」对账会误判为一致——§2.3 要求台账按「端点 × 分支」行，不按键名合行。
3. 动态键与通用渲染无法逐键枚举：`Object.entries(result_ref)`、`Object.entries(stats)` 等渲染面没有固定键集合——§2.4 定兜底处理：通用渲染面按「渲染器行为」断言（未知键原样呈现/省略，不得经固定标签表产出 undefined），不再逐键列。
4. 存量语义牵连：有些不一致改动会动数值语义（例如某字段前端与服务端对「比率」的理解不同，改一边会改另一边的数值含义）——§4 定死：数值语义牵连项一律标红停手、不顺手改，写入报告等 Martinez/总管裁决。
5. 文本内嵌数字不在结构契约内：多数命令只返回 `{ok, text, status}`，数值主张嵌在自由文本里（如「灵石 +500」），无法用键差集覆盖——§2.5 定边界：文本数字只做 P0 级抽查（已知 stone_loss 类 + 审计中发现的文本/字段矛盾），不承诺全文逐句对账；把这一点写进验收，不假装全量覆盖了文本。
6. Demo 模式本地捏造是另一类口径：v0.3.11 已把 3 处联机捏造收为 demo-only，但全仓 `state.demo` 分支仍有数十处（§0.2-F12）——§3 定 Demo 面单列，不与联机口径混行。

**第四步 · 举一反三。** 横向：CLI 是否同型——是，CLI 的 `render_*` 直接读同一批响应 dict（`res.get(...)`），同一字段缺失在 CLI 是静默空值、在网页是 undefined 拼串，表现不同但根因同类，纳入审计面（§3-D）；图鉴/仪式/入局 briefing 等只读呈现面是否同型——是，它们只认后端下发结构（workbench.js:633 注释口径），但 `entry`/`origin_card`/`gallery` 的键集合从未与 `_status_dict` 之外的 payload 出口对过，纳入审计面（§3-E/F）。纵向：契约层沉淀为后续发版可复检的资产——本轮的测试文件（§5）不是一次性脚本：服务端键集合 vs 前端引用键集合的双向差集断言、已知坏模式的全仓扫描、真实 payload 的 node 渲染执行，三类断言在以后每次改动响应形状或渲染口径时都会自动复检；台账文件本身是下一轮审计的基线（新增端点/字段时先补台账行再施工）。涟漪：修复方向一律「服务端是数据真相」（§4），前端不得为迁就旧渲染而要求服务端改数值；唯一例外是只增回显字段 `stone_loss`（§6），且它是纯加法、不改任何既有键的值。

**第五步 · 完善方案（收敛点，即本 Spec 的定死口径）。**
- **K1 · 全量的定义**：全量 = 全部可达的 `/命令` 分发分支（§2.2 的 193 分支清册）× 各自分支的真实响应键集合 + `_status_dict` + 登录/入局/转世/死亡 payload + ceremony `result_ref` + 三端渲染面；未覆盖的端点须在台账末尾显式列出并说明原因（§2.6），不允许以「已全量」掩盖未覆盖项。
- **K2 · 台账先行**：先出台账初稿并经评审逐项核销，再动手修 P0/P1；不许边修边补台账、不许先修后补（修过的项无对照即不可复核）。
- **K3 · 修复方向**：服务端是数据真相（§4）；数值语义牵连项标红停手。
- **K4 · 契约层**：三类断言（双向差集、全仓坏模式扫描、真实 payload 渲染执行）随本轮交付，缺一类即 §5 未验。
- **K5 · 移动端硬线**：mobile.js ≤1660 行 / mobile.css ≤27455B（三期硬线测试在先），超硬线停工回主策岗（§7）。

### 0.3 方案/任务边界冲突记账（逐条处置口径）

- **X1 · 台账位置二选一已定死**：任务简报允许台账放在 `docs/compose/contract-audit-ledger.md` 或 Spec 附录。处置：**定死前者为唯一台账位置**，Spec 附录只放台账的「统计摘要 + 未覆盖端点清单」索引，不放逐行台账（防两处台账漂移）。

## §2 · 审计方法论（本轮核心，必须可复核）

### 2.1 枚举前端消费点的方法

**第 0 步 · 别名清册（先做，后面的 grep 都以它为准）。** 前端不只用 `res.xxx` 一种写法。审计开工先产出三文件的别名清册：响应对象别名（`res`/`data`/`payload`/`resp`）、状态对象别名（`state.status`/`s`/`st` 等，以 `applyStatus`/`applyStatusM` 的入参与赋值点为准）、Demo 标志（`state.demo`）。清册本身是台账附录 A，grep 模式清单以清册为准绳，漏一个别名即漏一片消费面。

**grep 模式清单（三个文件全量跑，命中行逐行登记，命中 0 的模式也要在台账方法学节写「0 命中」）：**

| # | 模式（正则/字面，示意） | 抓什么 |
|---|---|---|
| G1 | `(res\|data\|payload)\.[A-Za-z_][A-Za-z0-9_]*` | 响应顶层键读取 |
| G2 | `(state\.status\|status\|s\|st)\.[A-Za-z_][A-Za-z0-9_]*`（以别名清册收敛） | `_status_dict` 键读取 |
| G3 | `\$\{[^}]*\}` 模板插值（含 `esc(...)` 内） | 拼串渲染点（undefined/NaN 的高发区） |
| G4 | `Object\.entries\(` / `Object\.keys\(` / `Object\.values\(` | 通用渲染面（§2.4） |
| G5 | `\?\.[A-Za-z_]+` 与 `\|\| / \?\?` 缺省 | 缺省口径（缺失时显示什么：空串/0/兜底值/捏造值） |
| G6 | `\.toFixed\(|\.toLocaleString\(|Math\.round|parseInt|parseFloat` | 数值格式化点（浮点噪声、比率/百分比口径） |
| G7 | `state\.demo` 全部命中 | Demo 本地捏造面（§3-G） |
| G8 | 写死中文键/枚举字面量（如 `stats\['...'\]`、中文键名、`"攻伐威能"` 类） | 服务端不存在的键（v0.3.11 同型复发） |
| G9 | `ceremony|result_ref|beats|asset_key` | 仪式呈现面（§3-F） |
| G10 | `entry|origin_card|gallery|omen_` | 入局/出身/图鉴/奇遇只读面（§3-E/F） |
| G11 | CLI：`res\.get\(|result\.get\(|char\.[A-Za-z_]+`（`cli/*.py` + `cli/views.py` 的 `render_*`） | CLI 消费点（§3-D） |

**动态键与通用渲染的兜底处理办法（§2.4）：** 通用渲染面（G4）不逐键列入台账，改为按「渲染器」行登记：渲染器位置 / 输入形状（对象/数组/标量）/ 未知键行为（原样呈现键名 / 省略 / 经标签表映射）/ 空值行为（null/undefined/空对象时是否整行省略）/ 结论。合格标准：未知键不得经固定标签表产出 undefined，不得对非数值调数值格式化，不得把缺失渲染成有含义的数字（如 +0）。`result_ref` 平铺（workbench.js:878）、纳戒 `Object.entries(stats)`（:5550）等现存通用渲染器逐个按此口径验收；不合格的渲染器记 P1，按渲染器修，不逐键打补丁。

### 2.2 服务端 payload 清单的来源

三路来源，缺一路即不完整：

1. **静态清册**：`server/world.py` 的 193 个 `action in (...)` 分发分支逐分支登记（分支名/行号/返回键集合/是否透传 `_status_dict`）；`_status_dict`（:4551–5060）逐键登记（含条件键：只在某分支/某状态下才出现的键须注明条件）；登录/注册（`join`/`login` 回退快照与 503 路）、死亡 payload（:919–931）、转世 `reincarnate`（:1004 起）、`build_entry`（`core/briefing.py:57`）等非 `/命令` 出口逐个登记；`core/` 规则引擎中直接构造响应 dict 的返回点（以 `/挖宝` 的 `TreasureEngine.dig`、` /捡漏` 内联构造、`attempt_breakthrough` 等为代表）登记其返回键。

### 2.3 台账格式（每个消费面一行）

台账唯一位置：**`docs/compose/contract-audit-ledger.md`**（X1）。每行字段（缺一不可，空值写「—」并注明原因，不得留空）：

| 字段 | 含义 |
|---|---|
| ID | `CA-001` 起顺序编号，全 Spec/报告引用以此为准 |
| 消费面 | 前端文件:行号 + 渲染位置（面板/页面/overlay 名） |
| 消费字段 | 前端读取的键路径（如 `res.stone_gain`、`status.equipped[].stats.power`） |
| 服务端来源 | 端点/分发分支 + 行号 + 返回该键的代码位置；无来源写「服务端从不下发」 |
| 对照结论 | 四值之一：**一致 / 不一致 / 前端兜底捏造 / 格式问题**（定义见 §2.3 下） |
| 严重级 | P0/P1/P2/P3/P4（定义见下） |
| 处置 | 修复（链接验收编号）/ 标红停手 / 定性不修（理由）/ 待复现 |
| 证据 | 真实响应抓取文件路径，或静态位置 + 既有测试名 |

**对照结论定义：** 一致 = 服务端在所有可达分支下发该键且形状与前端假设相同；不一致 = 键缺失于某分支、形状分叉（同键不同分支类型不同）、或值语义与前端假设不同；前端兜底捏造 = 服务端缺失/无值时前端凭空补一个有含义的值（联机模式，Demo 模式除外，另记）；格式问题 = 值正确但呈现格式错（比率当百分比、浮点噪声未截断、单位缺失/错、枚举中文与服务端字符串不符）。

**严重级定义：** P0 = 误导数值或阻断（错数、+0 实为 −40、面板不可达、联机捏造）；P1 = 可见 undefined/NaN/空白/错枚举；P2 = 格式/单位/小数口径不一致；P3 = 死键（前端读、服务端从不下发且渲染无可见异常）或仅 Demo 面问题；P4 = 记录性（口径已定死、无需改，仅备查）。

### 2.4 通用渲染与动态键（重申）

见 §2.1 末段。另：动态键来自服务端 `custom_metadata`、词缀 `affixes[]`、图鉴派生键等，不得要求服务端「把动态键枚举全」——审计只验渲染器对未知键的行为，不验动态键集合本身。

### 2.5 文本内嵌数字的边界

多数命令只返回 `{ok, text, status}`，数值主张嵌在自由文本里，键差集覆盖不到。边界定死：文本不逐句对账；只做 P0 级抽查——① 已知 stone_loss 类（§6）；② 审计中偶遇的文本/字段矛盾（同一响应内 text 说 A、字段说 B）；③ 数值格式类文本（如百分比）抽查 10 个高频命令。抽查结论记入台账「文本抽查」节，不混入逐行台账。

### 2.6 台账完整性的自我检验方法

四项断言，全部写进契约测试（§5），缺一项即台账未验：

1. **双向差集断言**：服务端响应键集合（静态清册 ∪ 真实抓取）与前端引用键集合（G1/G2 枚举）的双向差集——「服务端下发、前端从不读」的键列入「未消费键清单」（备查，不强制修）；「前端读、服务端从不下发」的键必须在台账中有对应行（死键 P3），差集中出现台账外键即测试变红。
2. **分支覆盖断言**：193 个分发分支逐个在台账中有「已抓取 / 静态登记 / 未覆盖（原因）」三态之一；未覆盖的端点清单须显式列出台账末尾并说明原因（前置状态不可达/需多人/需付费等），清单为空或全有原因说明方为通过。
3. **扫描集断言**：沿 v0.3.11 方法（`git ls-files *.js ∪ 工作树 rglob *.js`），全仓 JS 扫描集须含 workbench.js / app.js / mobile.js 三文件且无遗漏副本（根目录陈旧副本复现即变红，沿 `test_root_stale_frontend_duplicates_removed` 口径）。
4. **逐行复核**：台账每行须有证据链接（抓取文件或静态位置）；评审岗逐项核销时，任一行证据缺失即该行未验。

## §4 · 修复方向裁决

### 4.1 默认方向：服务端是数据真相

- 前端读取的键、形状、枚举值、数值单位，一律以服务端结算本体（`core/` 规则引擎 + `server/world.py` 分发返回）为准；前端按真相改渲染口径，不得要求服务端为迁就旧渲染改数值、改键名、改枚举。
- 例外只有 §6 的 `stone_loss`（只增回显字段，不改既有键的值）与 X4 的预批口径——其他新增键一律回主策岗裁决。
- 渲染侧缺失态口径：服务端合法缺失（某分支无该键）时，前端须显式呈现缺失态（整行省略或「—」），不得把缺失渲染成有含义的数字（+0、0%、无），不得拼串出 undefined/NaN。

### 4.2 数值语义牵连项：标红停手

审计中发现不一致、且改动会动数值语义者（例如：某字段在两处分支含义不同、比率与百分比口径牵连结算、单位换算牵连既有存档显示），一律按以下流程，不顺手改：

1. 台账该行严重级标 P0、处置写「标红停手」，并写清牵连链（改 A 会动 B 的数值/存档/既有测试）；
2. 不写修复代码，不改既有测试去迁就；
3. 汇总进 Spec §12 后的「标红清单」与最终报告，等 Martinez/总管裁决后再立轮次处理。

### 4.3 枚举/状态字符串、数值格式口径（定死）

- **枚举/状态字符串**：前端不得自造枚举中文；状态/品阶/ outcome 等字符串一律以服务端下发值为准呈现，映射表须覆盖服务端该字段的全部取值（新取值出现时映射表缺省为原值呈现，不得产出 undefined）。映射表缺省行为写进契约测试。
- **比率/百分比**：服务端下发比率（0–1 小数）与百分比（0–100）须在台账中按字段逐个注明，前端按注明口径渲染；同一字段在不同分支口径不同者记 P0（形状分叉）。
- **小数/浮点噪声**：数值渲染统一截断口径——沿 v0.3.11 的 `treasurePanelStatLine` 先例（2 位小数截断、零值/非数值整行省略），推广为全仓数值渲染的默认口径；例外须在台账该行注明。
- **单位**：灵石/修为/寿元/道心等量纲须与服务端字段语义一致（`stone_gain` 是灵石数、不是比率），单位缺失或错记者记 P2，单位错导致误读数值的记 P0。
- **时间戳**：`chosen_at/drawn_at` 类时间戳字段的呈现口径沿既有（豁免逐字段相等断言，沿 game-feel-phase3 §5.3 口径），不另立新口径。

## §6 · 已知两残留的处置归属（在范围内）

### 6.1 brute_force `stone_loss`：服务端只增字段

- **事实**（F2）：`core/treasure_system.py` brute_force 分支扣 40 灵石（`loss_stones = 40`），message 如实写扣款；返回 dict 无 `stone_gain` 键，`/挖宝` 分发以 `res.get("stone_gain", 0)` 补 0，前端显示「发掘灵石 +0」。
- **处置**：服务端在 `/挖宝` 分发 return 只增 `stone_loss: res.get("stone_loss", 0)`，其中 `stone_loss` 由 `TreasureEngine.dig` 各 outcome 分支如实填写（brute_force 为 40，其余 outcome 为 0；不得在分发层硬编码 40——分发层只透传引擎值）。前端宝图面板改读 `stone_loss` 呈现扣款行（扣款 >0 时显「灵石 −40」，为 0 时整行省略，不得再以 `stone_gain === 0` 推断无扣款）。验收见 §8/FX-01（真实 payload：brute_force 响应含 `stone_loss == 40` 且面板渲染「−40」无 +0；其余 outcome `stone_loss == 0` 且无扣款行）。
- **红线**：只增字段，不改 `stone_gain` 的既有语义与值，不改扣款本体（`core/treasure_system.py` 的扣款行一字不动）。

### 6.2 遗物分支结算面板不可达：先复现再修或定性

- **事实**（F3）：相关机制已定位（workbench.js:5236 仪式先行、:6129 有幕不开自有面板），完整复现链未跑通。
- **处置流程**：① 以 scar_created（遗物「纯阳离火印」）真实响应在桌面端复现：关闭得宝幕后结算面板是否可达、面板是否含遗物行；② 复现证实不可达 → 修（修面限于面板/仪式叠演顺序，不得改结算本体）；③ 复现证实面板本身无遗物分支渲染 → 定性为缺失渲染并修；④ 无法复现 → 台账记「未复现」并写清复现条件（种子/图 tier/分支），不硬修。验收见 §8/FX-02。
