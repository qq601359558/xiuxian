## §0 · 盘点核查结论（写 Spec 前已实测，任务前提有两处纠正）

本节是本轮最重要的盘点结果：任务书里的两处前提与仓库现状不符，设计按**实测现状**为准，开发岗不得按任务书原文的字面理解开工。

### C1 —— 真正在跑的桌面页不是 `app.js`，是 `workbench.js`（纠正任务前提）

| 位置 | 实测现状 |

| `web/app.js`（2462 行） | 遗留客户端：它读的 `#btnJoin` / `#username` / `#playerName` 等 id 只存在于**不对外托管**的 `web/prototype.html`；`web/README.md` 亦称「`app.js` / `style.css` 已弃用」 |

| 结论 | **移动版以 `workbench.js` 的行为契约为准**（登录/注册、`/action` 命令通道、五大主境视图语义），不得以 `app.js` 的 `feed/goals/world` 三页签结构为蓝本。`app.js` / `style.css` / `prototype.html` 本轮一律不动、不删、不复活 |

### C2 —— v0.3.3 并没有去掉宗门阵枢输入框（纠正任务前提）

- `remove-server-input.md` 已标注 **supersede**：移除方案不再实施。
- v0.3.3 实际落地（`218b5aa` / `d8f93f4` / `0b43abf`）：只改了**默认基址**，输入框 `#serverUrl` 仍在 `web/index.html:100-101`，页脚仍写「默认阵枢：`mn.20230803.xyz:8765`，换服可改」。
- 真正在跑的默认地址逻辑在 **`web/workbench.js:138-147`**（不是 `app.js` 开头；`app.js:6-18` 是同一规则的遗留副本，键名不同）：
  - 读 `localStorage["wb.base"]`；若是回环地址（`localhost` / `127.0.0.1`，可带端口）则**丢弃**；
  - 本机打开（`location.hostname` 为 `localhost`/`127.0.0.1` 或协议 `file:`）→ `http://127.0.0.1:8765`；
  - 否则 → `http://mn.20230803.xyz:8765`；
  - 登录成功后把基址写回 `wb.base`（`workbench.js:6537` / `6602`）。
- **移动版必须逐字复用同一口径**（同一键名 `wb.base`、同一丢弃规则、同一两档回落），不得另 invent 一套，不得读 `td_base`（`app.js` 的旧键）。

### C3 —— 静态托管实际是双轨制（`_serve_static` 与 `_static_response` 并存）

`server/app.py` 里有两套静态逻辑，设计必须同时写清：

| 机制 | 位置 | 行为 |
|---|---|---|
| `_serve_static`（`do_GET` 前段，`:179` 先行） | `server/app.py:107-165` | `/`、`/index.html`、`/web`、`/web/`、`/web/index.html` → `index.html`；`/web/<任意文件>`、`/images/<任意文件>` 按前缀映射（带三轮 `unquote` 与 `..` / `\` / `%00` 拦截，`resolve()` 后 `relative_to` 校验）；`/workbench.css`、`/workbench.js`、`/app.css`、`/app.js`、`/style.css` 走 `_ROOT_STATIC_FILES` 精确文件名常量 |
| `_static_response`（`do_GET` 末段，`:332`，全部 API 路由之后） | `server/app.py:73-104`，表 `_STATIC_PAGES` | 5 条精确路径 → 固定文件名常量：`/`、`/index.html` → `index.html`；`/app.js`、`/style.css`、`/ailog.html` 各对本名；未命中返回 `False` 走 404。文件名绝不由请求路径拼接 |
| 响应头 | 两处一致 | `Cache-Control: no-cache`，带 `Content-Length`，`Access-Control-Allow-Origin: *`；Content-Type 查 `_STATIC_CONTENT_TYPES`（已含 `.html` / `.js` / `.css`，**无需扩展**） |

推论（写进设计 D5）：

1. 新文件 `mobile.html` 今天不改服务端也能经 `/web/mobile.html` 被取到（走 `_serve_static` 的 `/web/` 前缀分支）——**但 Spec 不许依赖这条旁路**：移动版入口必须是白名单里的**一级精确路径**（`/mobile.html` 等），与桌面入口同等地位。
2. `/web/` 前缀分支今天事实上能取到 `web/` 下任意文件（含 `prototype.html`，与 `test_prototype_not_served` 只断言 `/prototype.html` 404 的口径有缝隙）——这是**既有口径缺口，本轮不扩大、不修复**（见 Out of Scope），新条目一律走精确路径，不新增任何前缀映射。
3. `_serve_static` 在 `do_GET` 里先于 API 路由执行：新增静态路径不得与任何 API 路径重名（`/mobile*` 与现有 API 无冲突，见 M-14）。

## 阶段一 · 五步推演（简写，方法见 requirement-evaluator）

### 1. 本质解构

- **表层需求**：给游戏单独做一套手机端页面，与桌面端两套独立页面，接口与数据完全共用，桌面端不动。
- **本质诉求**：手机是 Martinez（及未来真人试玩玩家）实际最常用的入口；当前手机体验不是「有点挤」，而是核心循环不可用——登录后命盘/行囊被裁、舞台看不见、页签折行。用户要的是**手机上能完整玩一局**，不是「手机也能打开」。
- **伪需求排除**：继续在 780px 断点里修修补补是伪路径——v0.2.4 已证明同一套 DOM/同一套栅格在 390px 下修不出拇指可达的单列操作流；两套页面是用户已批准的解法，不再论证「一套响应式是否够」。
- **验收标准**：见 §验收 M-1～M-20；核心是「390×844 与 390×667 两档真机尺寸下，不横向滚动、不裁剪、核心循环全通；桌面 1280 宽像素级零变化」。

### 2. 可行性评估

- **技术可行性：高**。纯前端 + 托管白名单改动：新文件 `mobile.html` / `mobile.js` / `mobile.css`，服务端只加 3 条精确白名单；无 `core` 改动、无数据模型改动、无新 API；`workbench.js` 的 API 语义（`/register` / `/login` / `/action`）可直接复用。
- **性能/成本**：新增静态文件约与桌面页同量级；运行时无新增轮询口径（复用既有命盘+同场轮询节律，不得另起更高频轮询）；分流脚本为 `<head>` 内联约 20 行，桌面首屏零可感知开销。
- **唯一中风险**：双客户端并行后的**漂移风险**——以后接口/命令变了，只改一端会让另一端悄悄掉队。用契约测试对冲（M-17），不用「共用一份 JS」对冲（两端 DOM 结构已不同，硬共用只会把移动版拖回桌面结构）。

### 3. 不足与盲区

1. **分流边界**：平板/折叠屏/桌面窄窗口（宽 ≤780px）会被划入手机——须有显式偏好 + `?view=` 逃生口（D1-④⑤），否则桌面用户缩窗即被劫持。
2. **跳转循环**：双向切换 + 自动分流三者叠加最易写出循环（A→B→A）；须写死「目标页即当前页时不跳」「显式偏好优先于自动分流」两条铁律（D1-③）。
3. **登录态跨页**：`wb.token` 存在 `localStorage`，两页同源故天然共享；但若移动版另起键名（如 `mb.token`）则切换即掉线——必须复用 `wb.*`（D2-⑦），并在验收里覆盖「桌面登录 → 切手机版 → 免登录直达」（M-7）。
4. **输入法与 iOS 缩放**：移动端 `<input>` 字号 ＜16px 时 iOS 聚焦自动放大整页；桌面 780px 规则已有此口径（`style.css` 旧规则），移动版必须继承（D2-⑥）。
5. **弱网与 CDN**：桌面页依赖 Tailwind CDN 与 Google Fonts；手机弱网下首屏可能长时间无样式。移动版自包含 CSS，不新增 CDN（D2-⑧）。
6. **旧存量地址**：玩家浏览器里可能还存着 `wb.base`（含回环值）与 `td_base`；移动版只读 `wb.base` 并执行同一丢弃规则，不得读 `td_base`（D2-⑨）。
7. **离线演示**：桌面门庭有「玄黄镜演（离线演示）」按钮（不走服务器基址）；移动版门庭是否保留，见取舍表 F-02——保留（门庭对等，零接口成本）。
8. **横竖屏旋转**：390×844 竖屏为验收基准；旋转到 844×390 横屏时不得出现横向滚动与底部导航遮挡输入框（M-11 覆盖旋转抽查）。

### 4. 举一反三

- **横向**：同类「一端凑合用」的只有手机端；`ailog.html` 是运维页、平板无独立需求，本轮不扩展到第三套。
- **纵向**：将来若出第三端（如小程序/桌面客户端），分流偏好键 `wb.viewpref` 与「显式偏好优先、目标即当前不跳」的防循环规则可直接复用；移动版若沉淀出「命令快捷条」组件，桌面端后续可反向借鉴，但本轮不做（Out of Scope）。
- **涟漪面**：`server/app.py`（白名单两处）、`tests/test_web_hosting.py`（托管断言）、`tests/test_qa2_frontend_contract.py`（前端契约解析对象新增移动页）、`docs/gray-runbook.md`（玩家入口文案多一行移动版地址）、`web/README.md`（入口说明）。**不触及**：`core/`、`server/` 除白名单外的全部路由、`data/` 存档、CLI。

### 5. 完善方案

- **推荐路径**：客户端分流（D1 方案 B）+ 独立移动三件套（D2）+ 双轨白名单同步加条目（D5）+ 契约测试锁双端（M-17）。
- **备选方案对比**：
  - A 服务端按 UA 分流 `/`：无闪烁，但服务端要读 UA、破坏「`/` 即桌面版」的既有心智、`file://` 用法失效、缓存与测试面变大——**否决**。
  - C 单页内按宽度切换两套 DOM：等于把两套页面塞进一个文件，首屏体积翻倍、桌面回归面最大——**否决**。
  - D 继续修 780px 断点：v0.2.4 已证伪——**否决**（用户原话已批准两套）。
- **分阶段**：本 Spec 只覆盖 MVP（核心循环全通 + 分流 + 零回归）；移动版富面板（宗门/坊市完整面板等）按取舍表 Tier 2 先以命令可达，后续另立工单，不在本轮扩围。

## Problem

1. **手机不可玩**：390px 下命盘+行囊曾被挤压裁剪（C4 实测量）；390×667 矮屏舞台仅约 180px；天道录页签折行；底部敕令台在小屏下与内容争抢空间，拇指够不到常用操作。
2. **一页两用已到头**：桌面工作台是 1720px 宽的多栏工作台（顶栏五主境 + 右抽屉 + 底部敕令台），靠断点硬挤进 390px 只会越挤越碎；再修断点会同时动桌面布局，回归面不可控。
3. **入口没有手机心智**：玩家手机打开根地址 `http://<addr>:8765/` 只能得到桌面页，没有「这是手机版」的分流，也没有手动切换的记忆。
4. **约束**：接口与数据完全共用（不新增端点、不改数据模型）；桌面端行为零变化；旧存档零改动。

## Design

### D1 · 分流方案（主策裁定：方案 B 客户端分流）

**裁定：客户端分流。** 根地址 `/` 与 `/index.html` 永远返回桌面版；分流发生在浏览器内的一小段 `<head>` 内联脚本。理由：

- 桌面零回归：服务端不碰请求分发逻辑，只加白名单条目；桌面首屏只多一段约 20 行内联脚本，不改任何既有 DOM id、样式与行为；
- 可测试：分流规则是纯前端判定（偏好键 + 宽度 + UA），Puppeteer 可在无服务端改动的情况下全覆盖；
- `file://` 与多服打开方式不受影响（服务端分流在这些场景下无从判定）；
- 代价唯一：手机首次打开需一次 `location.replace` 跳转（不留历史记录，返回键不回跳桌面页），可接受。

**D1-① 分流判定（按优先级从高到低，命中即停）：**

1. URL 查询参数 `?view=mobile|desktop`：仅本次加载生效，**不写偏好键**（逃生口，见 D1-⑤）；
2. `localStorage["wb.viewpref"]` 显式偏好：`"mobile"` 或 `"desktop"`，命中即按偏好进对应页；
3. 自动判定：`isMobileDevice()` 为真 → 移动版，否则桌面版。其中 `isMobileDevice() = window.matchMedia("(max-width: 780px)").matches || /Mobi|Android|iPhone|iPad|iPod|Mobile/i.test(navigator.userAgent)`（780px 与既有窄屏断点口径一致；任一条件满足即判手机——大屏手机横屏仍走移动版，桌面窄窗缩到 ≤780px 亦判手机，误判由 D1-⑤ 兜底）。

**D1-② 分流脚本位置与形态：**

- `index.html` 与 `mobile.html` 的 `<head>` 内各放同一段内联脚本（约 20 行，**不得外链**，避免外链失败导致分流失效），在 `<body>` 渲染前执行；
- 脚本只做一件事：算出目标页，若目标页 ≠ 当前页则 `location.replace(目标 URL)`；目标页 ＝ 当前页时**什么都不做**；
- 跳转保留查询参数与 hash（除 `view` 参数本身外）；跳转目标：桌面 → `/mobile.html`，手机 → `/index.html`（根 `/` 视为桌面页）。

**D1-③ 防循环机制（铁律，验收 M-3 逐条覆盖）：**

1. 目标页即当前页时不跳转（以 `location.pathname` 末段判定：`/`、`/index.html` 归桌面，`/mobile.html` 归手机）；
2. 显式偏好优先于自动判定，且偏好指向当前页时不跳转；
3. 单次加载最多跳转一次（脚本执行后即结束，无定时器、无二次判定）；
4. `?view=` 仅本次生效且不写偏好，杜绝「参数写死偏好 → 每次都被带回另一端」的循环；
5. 两页的分流脚本判定函数**同一口径**（同一 `isMobileDevice` 定义、同一偏好键名），不得各写各的。

**D1-④ 手动切换入口（必须有，且必须记住选择）：**

- 桌面版：在门庭（未登录）与顶栏（已登录）各放一处「手机版」入口（文案定为「手机版」，位置由前端岗在 Spec 约束内自定，门庭页脚或顶栏右端均可）；点击 → 写 `wb.viewpref="mobile"` → 跳 `/mobile.html`；
- 移动版：在门庭与底部导航区（或「操作」页内）放「桌面版」入口（文案定为「桌面版」）；点击 → 写 `wb.viewpref="desktop"` → 跳 `/index.html`；
- 切换后偏好**持久化**（`localStorage`），下次打开根地址直接进偏好页，不再自动判定；
- 另须提供「恢复自动」：移动版「操作」页（或门庭页脚）放「跟随设备自动选择」入口，点击清除 `wb.viewpref`，下次按自动判定。

**D1-⑤ 逃生口：**

- 任何时候带 `?view=desktop` 打开根地址即本次进桌面版（不写偏好）；`?view=mobile` 同理；
- 该参数用于：桌面窄窗被误判、偏好被误点、验收时强制指定版本。

**D2-⑧ 样式与依赖：**

**D2-⑨ 轮询与刷新：**

## 真正需求条目（收敛结论，开发与验收的唯一依据）

1. **问题**：手机端核心循环不可用（命盘/行囊裁剪、舞台 180px、页签折行），断点修补已证伪。
2. **行为契约**：两套独立页面（桌面 `index.html` + 移动 `mobile.html` / `mobile.js` / `mobile.css`），接口与数据完全共用；手机开根地址自动进移动版，桌面仍进桌面版；双向手动切换且记住选择；偏好优先、目标即当前不跳、单次加载最多一跳，永不循环。
3. **边界**：桌面文件只许 D4 白名单内的最小改动；服务端只加白名单条目；不碰 `core`、数据模型、存档、API；不做第三端、不做 PWA、不移植桌面富面板与 AI 日志页。
4. **验收标准**：M-1～M-20，含 390×844 / 390×667 / 桌面 1280 三档量测与截图清单。
5. **不做范围**：见 Out of Scope 1～7。
