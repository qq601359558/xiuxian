# Spec：账户层死亡资金归集与死后建角（account-death-rework）

> 状态：已交付 v0.2.2-gray.4（main，验收：连续 3 次全量 674 passed 0 failed）。

- **状态**：Spec（阶段一产出，待实现岗接手；本文件不含业务代码改动）
- **基线**：`main = 3cafcc6`（v0.2.1-gray.3）；隔离分支 `feat/account-death`，工作区 `.worktrees/account-death`
- **依据**：仓库 `AGENTS.md` 阶段一 + `.agents/skills/requirement-evaluator/SKILL.md` 五步推演
- **Martinez 定死规则**（本 spec 原样落地，不得反向修改）：
  1. 角色死亡后金额保留在账户层，依然挂原有玩家名称（账户名保留）。货币类默认归账户，角色成长类默认不保留、按现有历世规则处理；逐项资产写明归属与理由。
  2. 死者挂起资金一并定掉（此前 QA 遗留三项）：死者寄售成交款、死者拍卖冻结出价退款与中标物品、死者议政票——资金类一律结算到账户；物品/票权类给出与规则一致的处理并写明。
  3. 玩家登录账户时，若现有角色已死亡，可以创建新角色继续游玩；新角色挂同一账户名、用账户层金额。创建流程双端（CLI + web）可用。
  4. 与历世／飞升榜／传说系统不得冲突：旧角色历世落账照旧，同一笔钱不得在角色与账户两处重复存在（资金守恒）。
  5. 界面范围：死亡结算页、账户钱包展示、死亡后建新角色的引导流程三处 web 界面要清晰好看（本 spec 定视觉与交互要点）；不做全站 UI 翻新。

## §0 五步推演摘要（requirement-evaluator）

### 0.1 需求本质解构

- **表层需求**：死后钱还在、登录能建新角继续玩。
- **本质意图**：死亡不应是经济清零。当前死亡的实际语义是「旧行被覆写＋新角白手起家」，货币随行消散（或封存在死行里），与玩家对「我的钱」的直觉冲突；同时 QA 遗留三项（寄售／拍卖／议政）证明死亡时刻根本没有统一的挂起资金结算点。
- **系统定位**：这不是一个新玩法，而是一次**记账主体变更**：货币的归属主体从「角色行」升级为「账户」，死亡从「行覆写」升级为「行覆写＋账户结算」。触点：死亡结算双入口、寄售／拍卖／议政／典当四个挂起资金通道、登录／转世两条建角路径、web 三处界面。
- **验收标准**：见 §4（每条可观察：命令、接口、测试）。

### 0.2 可行性诊断

- **技术可行性：高**。全部是现有引擎上的记账路由改动，无新服务、无新依赖：钱包可复用 `player_legacy` 账户行（见 D1），死亡结算已有 `death_settled` 幂等守卫与双入口，拍卖／寄售已有落账单点（`AuctionEngine._apply_bid`／`MarketEngine.complete_sale_payment`）。
- **系统影响面**：`core/legacy.py`（结算入口）、`core/account.py`（账户概念）、`core/trade.py`（拍卖）、`core/market.py`（寄售）、`core/council.py`（议政）、`core/pawn.py`（典当）、`server/world.py`（`join`／`_settle_if_needed`／`reincarnate`）、`server/app.py`（`/login` 行为变更）、`cli/main.py`（`ensure_alive_player`／`settle_and_reincarnate`／`prompt_reincarnation`）、`web/app.js`＋`web/index.html`（死亡 modal 与状态块）、`storage/db.py`（`MarketListing` 补 `seller_user_id` 字段）。

### 0.3 不足、盲区与风险（推演中发现，全部已在本 spec 中闭环）

1. **行覆写断链**：`characters.user_id UNIQUE` ＋ `CharacterRepository.save` 的 `ON CONFLICT(user_id)` 覆写，意味着转世即销毁旧行。任何留在角色行里的钱、票、单都会在转世瞬间失去寻址——这是钱包必须脱离角色行的根本原因（冲突 C1）。
2. **按名／按 id 寻人双陷阱**：寄售付款按名查（`get_by_name`），转世后同名会付给新角、异名会丢钱；拍卖按 id 查失败后按 `user_id` 兜底（`_find_by_id_or_user`），转世后会把旧单的钱／物解析到新角（冲突 C3／C4）。
3. **一户两票**：议政票按角色 id 记在场次 `votes` 里，死亡不清除；若在场次内转世，新角（新 id）可再投一票（冲突 C5）。
4. **双端登录语义分裂**：web `/login` 经 `WORLD.join` 对死者**自动**建新角（且跳过道统加成选择），CLI 却是交互式 y/n 选择；本 spec 统一为「登录只报死讯＋钱包，建角须玩家显式确认」（冲突 C2，行为变更，见 §2.6）。
5. **死亡结算双入口**：CLI（`settle_and_reincarnate`）与 server（`_settle_if_needed`）各调一次钩子＋结算，钱包结算必须同时进两入口，否则一端漏扫（冲突 C7）。
6. **旧存档不可逆**：已转世覆盖的旧行无法追回（无 char id 存档，`past_lives` 仅留最近 10 世且无 id）；迁移只能覆盖「已死未转世」的行，须诚实声明，不得凭空补账（见 §5）。
7. **重复记账**：钱包入账必须以业务单据 id（寄售单 id／拍品 id／死者角色 id）为幂等键，防结算重跑与崩溃重放导致双倍入账（见 §2.7）。

### 0.4 举一反三

- **横向**：同类「挂起资金」不止 QA 三项——典当 OPEN 票（本金已付、物品在押）、悬赏预付金（已预付、无挂起）、当面交易会话（内存态）都须在死亡结算时给出口径，否则下一次 QA 还会发现第四、第五项。本 spec 在 §2.4 中逐项定掉。
- **纵向**：钱包一旦成为账户级余额，未来「跨世赠予／拍卖行直付钱包／月俸入钱包」都会自然来问。本 spec 预留钱包模型（余额＋流水），但**不**开放生前存入、钱包直付、跨户转账（见 §3），避免钱包退化成第二个寄存处（`vault_stones` 已承担此职）。
- **涟漪**：钱包绝不参与现有价格／战力／榜单计算（飞升榜分＝境界＋道统点＋享寿，`core/ascension.py`；现世六榜只读存活角色，`core/leaderboard.py`）。钱包余额不计入任何榜单资产分——否则死亡 sweep 会扭曲榜单。

## §1 Problem：现状审计（读代码所得，非记忆）

### 1.1 账户与角色的关系（现状）

- **认证账户**：`storage/db.py` 的 `accounts` 表（`user_id` PK、`username` UNIQUE、密码盐哈希），`core/account.py` 的 `register`／`login`（用户名 2–16 位中文／字母／数字／下划线，密码 ≥6 位）。认证表**没有任何经济字段**。
- **账户级元进度**：`storage/db.py` 的 `player_legacy` 表（`user_id` PK），`core/legacy.py` 的 `LegacyAccount`（`points` 道统点、`total_lives`、`past_lives` 最近 10 世、`death_times` 最近 20 次）。这是全库**唯一**按账户聚合、不随角色行覆写而消失的游戏数据行。
- **角色行**：`characters` 表 `user_id UNIQUE`，`CharacterRepository.save` 用 `ON CONFLICT(user_id)` 覆写。**一个账户在任何时刻只有一行现世角色**；转世＝新 `Character`（新 id）覆写旧行。旧世除 `past_lives` 摘要与 `world_chronicle` 文本外不留结构化记录。
- **CLI 无账号体系**：`cli/main.py` 的 `USER_ID = "local_player_01"` 写死，启动即 `ensure_alive_player()`。CLI 的「登录」＝加载本地账户；不新增 CLI 账号密码登录（见 §3）。
- **Web 账号体系**：`server/app.py` 的 `/register`（注册＋`WORLD.join` 建首世）与 `/login`（登录＋`WORLD.join`）。`WORLD.join`（`server/world.py`）对死者的分支是**先 `_settle_if_needed` 再直接 `create_new_character`**——登录死者＝静默建角，跳过道统加成选择，与 CLI 的 y/n 选择不一致（冲突 C2）。

### 1.2 死亡结算现状（双入口，资金零处理）

- **CLI 入口**：`cli/main.py` 的 `settle_and_reincarnate`：若 `death_settled` 为假，依次调 `PetEngine.on_owner_death`（灵宠殁）、`FarmEngine.on_owner_death`（灵田荒废）、`QuestEngine.on_owner_death`（委托消散）、`PromiseEngine.on_owner_death`（诺言 DISSOLVED），再调 `LegacyEngine.settle_death`（道统点入账、归档前世），然后问「是否立刻转世」＋轮回门（`check_reincarnate_gate`，连续极速送死时锁转世）。**全程不碰灵石、寄售、拍卖、议政、当票**。
- **Server 入口**：`server/world.py` 的 `_settle_if_needed`（同款四钩子＋`settle_death`，`death_settled` 为真时直接返回），被 `join`、`reincarnate`、心魔致死等路径调用。`reincarnate`（`/转世`）在结算后建新角＋消费道统加成（`apply_birth_boosts`，其中 `stones` 加成给新角 ＋150 灵石）。
- **死亡判定**：`CharacterStatus.DEAD` 或 `lifespan.is_dead()`；`can_use_market`（`core/trade.py`）对死者禁交易，`CouncilEngine.vote`／`lobby` 对死者前置拒绝，`PawnEngine.pawn_item`／`redeem_item` 对死者拒绝——**生前禁令齐全，死后结算缺失**，这正是 QA 遗留的根源。

### 1.3 挂起资金三项的现状实测结论（QA 报告原文口径，本 spec 采信并裁定）

- **寄售**：死者卖单仍可成交，货款入**死者角色行**（`complete_sale_payment` 按 `seller` 入账）；转世后新角零继承，钱封存在旧行（未转世时）或按名查不到／查到新角（已转世时，见 C3）。
- **拍卖**：死者出价被超价→冻款退回死者行；死者领先落槌→拍品入死者行囊、卖家照常实收；卖家死后流拍→拍品退回死者行囊。`_apply_bid` 的超价退款与 `settle_expired`／`_settle_buyout` 的落账均以角色行（`get_by_id`，失败按 `user_id` 兜底）为目标。
- **议政**：已投票者死亡，其票在 `tally` 中仍计入（QA 实测 1:1 平局成立）；`votes` 按角色 id 记，死亡不清除。

### 1.4 冲突点清单（现状 vs 新规则）

| ID | 冲突 | 后果（若不改） |
|----|------|---------------|
| C1 | 钱包无处落账：角色行会被覆写，认证表无经济字段，`player_legacy` 只有道统点 | 钱随行覆写而消失，或封存在死行里无法取出 |
| C2 | Web `/login` 对死者自动建角（`WORLD.join` 死者分支），跳过加成选择；CLI 却是 y/n 选择 | 「登录时可以建新角」被偷换成「登录时必定建新角」，且双端不一致 |

## §2 Design

### 2.1 记账原则（实现岗必须遵守，评审逐条核对）

1. **资金守恒**：任何一笔钱在任意时刻只存在于一个余额里（角色随身／角色寄存／拍卖冻结／钱包）。划转＝一边减、一边加，同一调用内完成；禁止「复制式入账」（只加不减）。
2. **钱包是账户的唯一死后归宿**：所有死后资金路由的终点都是钱包，不得以「付给新角」「付给死行」代替。
3. **死行清零**：死亡 sweep 完成后，死者行的 `spirit_stones` 与 `vault_stones` 置 0。此后任何仍以旧角色 id 为目标的付款都是 bug，须按 §2.5 路由改道钱包（清零让这类 bug 以 0 可见，而非静默错付）。
4. **单据幂等**：每笔钱包入账以业务单据 id 为幂等键（寄售单 id／拍品 id／死者角色 id），入账前查流水 `ref`，已存在则跳过（防重跑、崩溃重放、双入口重复调用）。
5. **快照不可逆**：已结算的议政场次、已落账的历世（`past_lives`）、已写的大事记／传说／飞升榜均不改写。死亡 sweep 只动未结算态（OPEN 单／OPEN 票／未结算场次）。
6. **价格与费率零变更**：拍卖成交抽成（CLI 帮助口径：5%）、寄售手续费（`list_item` 现行费率）、当铺五折／赎回价、道统点公式、轮回门阈值全部不动。本 spec 只改**钱去哪**，不改**钱多少**。

### 2.2 数据模型（推荐形态，实现岗可等价调整但须守 D1／D2）

- **`LegacyAccount` 扩展**（`core/legacy.py`，`player_legacy` 行 JSON 内，零改表）：
  - `wallet_stones: int = 0`（账户钱包余额，≥0；任何写路径须钳制下限 0，禁止负数落库）。
  - `wallet_ledger: List[WalletEntry] = []`，每条 `{ts, kind, amount, ref, note}`；`kind` 取值：`death_sweep`（死亡归集）、`consignment_sale`（寄售成交）、`auction_sale`（拍卖成交净额）、`auction_refund`（拍卖冻款退还）、`wallet_withdraw`（提取到角色，负数记账）；`ref` 为寄售单 id／拍品 id／死者角色 id／`withdraw:<ts>`；流水只保留最近 50 条（截断时保留总额字段不受影响——余额是独立字段，不由流水重算）。
- **`MarketListing` 扩展**（`core/market.py`）：`seller_user_id: str = ""`（与 `AuctionLot.seller_user_id` 同口径）。新单在 `list_item` 时由卖家 `user_id` 写入；旧单默认 `""`，迁移见 §5。
- **不新增表**：不建 `account_wallet` 表，不动 `accounts` 认证表，不动 `characters` 表结构。钱包随 `LegacyRepository.save` 落盘，与道统点同一行、同一事务语义（现有仓储是单行 upsert，无跨行事务；实现岗须保证钱包入账与单据状态变更的保存顺序见 §2.7）。

### 2.3 死亡结算新流程（双入口同款步骤，顺序即契约）

在既有 `settle_death` 调用**之前**（CLI 的 `settle_and_reincarnate` 与 server 的 `_settle_if_needed` 两处，缺一不可）插入「资金归集」步；`death_settled` 仍为总守卫，资金归集内部再以单据 `ref` 幂等（防迁移补扫与重跑叠加）：

1. **归集随身与寄存**：`wallet += spirit_stones + vault_stones`，记 `death_sweep` 两条（或一笔合计＋明细 note，明细必须可区分随身／寄存）；随后死行两字段置 0。
2. **拍卖领先出价退款＋拍品回起拍**：遍历 `AuctionLot` 的 OPEN 单，凡 `leader_user_id == 死者 user_id` 者：退 `current_bid` 入钱包（`auction_refund`，`ref = 拍品 id`）；该单 `leader_*` 清空、`current_bid` 回 `start_price`、`bid_count` 回 0（回起拍态；此前被超价者早已在 `_apply_bid` 时退过款，故无其他 frozen 资金——此不变量须由测试钉住）。
3. **议政票作废**：遍历死者所属宗门的未结算场次，从 `votes` 中删除键为死者角色 id 的票并保存会话（已结算场次不动；见 §2.4 裁定 3）。
4. **当票没收**：对死者的 OPEN 当票执行与 `settle_expired` 同口径的没收（票 → FORFEITED，物品以赎回价挂当铺寄售，卖家为当铺）；本金**不另记**（已在步骤 1 的随身灵石中）。
5. **既有四钩子＋道统结算**：灵宠／灵田／委托／诺言钩子与 `LegacyEngine.settle_death` 原样执行（顺序不变；资金步在前，保证道统结算展示时钱包余额已是终态）。
6. **落盘与留痕**：`LegacyRepository.save`（钱包＋道统点）、`CharacterRepository.save`（死行清零后状态）、`ChronicleRepository.record` 一条「资金归集」大事记（金额合计＋钱包余额，供审计）。

> 例外：NPC 死亡（`user_id` 以 `npc_`／`ai_npc_` 开头）不走钱包（NPC 无账户行；`LegacyRepository.get_or_create` 对 NPC 的行为保持现状，不得为 NPC 建钱包）。测试用 `t_` 前缀账号按 `leaderboard._is_player` 口径同样排除。

### 2.5 死亡挂起三项的最终裁定（QA 遗留三项，定死规则 2 的落地）

**裁定 1——死者寄售成交款 → 账户钱包；OPEN 单保留待售。**
- 死亡不撤单（与 QA 报告中「卖家死亡即自动撤单退物」的备选口径**相反**，理由：物品已离囊，撤单无归处；留单＋成交款入钱包才是资金与物品双闭环）。
- 成交路由（新规则，替代按名查找）：`complete_sale_payment` 的调用方（CLI 与 server 的买寄售 handler）须按 `seller_user_id` 路由——卖家现世角色存活且 id 与单据一致→付角色行（生前成交旧口径）；否则→付该账户钱包（`consignment_sale`，`ref = 寄售单 id`）。`seller_user_id` 为空的旧单按 §5 回填／预检规则处理。
- 新角不得撤旧世单（撤单须卖家角色 id 一致；新角 id 不同即拒绝），旧单与新世隔离。

**裁定 2——死者拍卖冻结出价 → 死亡时退还账户钱包；中标物品不交付死者。**
- 主路径（死亡 sweep，§2.3 步骤 2）：死者为领先者的 OPEN 单，冻款全额退钱包，拍品回起拍（`leader_*` 清空、`current_bid = start_price`、`bid_count = 0`），可被他人重新竞价。
- 卖家路径：死者为卖家的 OPEN／PENDING 单留场待结；落槌净额（扣现行抽成）入卖家账户钱包；一口价路径（`_settle_buyout`）同规则。
- 兜底路径（漏扫防御，如死亡发生在未走 sweep 的旧路径）：`settle_expired` 落槌时若领先者已死（按 `leader_user_id` 查：无存活对应角色，或角色已死）→ 冻款退领先者钱包，拍品**不交付**，改为：卖家存活→物品还卖家（按流拍计，`EXPIRED`）；卖家亦死→拍品消散（沿用现有先例）。本路径不得产生「钱物双得」。
- 死者为卖家的流拍：拍品退回逻辑同上（卖家已死→消散，不回新角行囊）。

**裁定 3——死者议政票 → 未结算场次作废；已结算场次快照不变。**
- 与 QA 报告中「票既出不撤」的备选口径**相反**，理由：票权绑定在世弟子身份；若保留死者票＋新角同场再投，同一账户两票，破坏多数决；且新角须重入宗门才有票权，作废后不存在票权真空争议。
- 死亡 sweep 清除死者所属宗门未结算场次 `votes` 中键为死者角色 id 的票（保存会话；结算时 `tally` 按清除后计票）。
- 已结算场次的 `result`（支持／反对／效果）一律不动——历史快照不可逆。
- 游说（`lobby`）：长老立场位移已记入场次 `lobby_steps`（长老侧状态），不回滚；游说已付灵石沉没不退（费用发生在生前，属已消费）。

### 2.6 登录与建角流程（双端）

**Web（行为变更，评审须重点核对）：**
- `POST /login`：账号密码通过后，若现世角色已死／寿尽→**不再调用 `WORLD.join` 的自动建角分支**，改为返回死者 payload：`{ok: true, dead: true, username, death_cause, legacy（道统点／世数／加成目录）, wallet（余额＋最近流水）, settlement（资金归集明细，若本次刚结算）}`；会话 token 保持有效且可用于 `/转世`（`reincarnate` 已有按 `user_id` 取旧行＋结算的逻辑，须确认 token 在死者 payload 下不被 `join` 的新角覆盖）。
- `POST /register`：全新账户（无角色行）仍自动建首世，不变。
- 匿名 `/join`（无 `user_id`）：保持现状自动建角；**带 `user_id` 的 `/join` 且现世角色已死时，不自动建角**，改为返回与 `/login` 死者分支同款 `dead:true` payload（评审 M2 明文规则：按 C2 立法意图，消除“登录时必定建角且跳过加成选择”；匿名无 `user_id` 时无此拦截，仍自动建角）。
- 匿名路径的钱包（评审 S9，有益偏离，修订原“匿名路径不建钱包”一句）：`lan_` 匿名用户同样走钱包——其 `user_id` 即 `lan_<随机>` 键，死亡 sweep 以该键建 `player_legacy` 行并归集；匿名用户无 `accounts` 认证行，但钱包键与认证账户同口径（按 `user_id`），故不存在“无账户可挂”的问题。原句“匿名路径不建钱包”作废。
- `/转世`（显式建角）：在既有逻辑（结算若需→建角→道统加成）前加两步：先跑 §2.3 资金归集（含迁移补扫，见 §5），再建角；返回体追加 `wallet`（余额＋归集明细），前端据此刷新钱包展示。
- 会话恢复（`restore` → `/look` 报 `dead` → `showDeath`）：沿用既有死者 modal 入口，内容扩展为 §2.8 的死亡结算页。

**CLI（流程不变，展示扩展）：**
- `ensure_alive_player`：死者→先跑资金归集并展示死亡结算页（§2.8），再沿用 y/n 提问＋轮回门；选 n 或被门挡下时沿用现有退出／静候逻辑（道统点与钱包均已落账，不丢失）。
- `prompt_reincarnation`：首行展示钱包余额（「账户钱包 X 灵石（户名：<username／local_player_01>）」），出生后追加一行提取指引（「新角随身 150 灵石；账户钱包可用 `/钱包` 查看、`/钱包提取 <金额>` 取用」）。道统加成选择流程不变。
- CLI 的 `USER_ID` 固定键即钱包键（`local_player_01` 的 `player_legacy` 行）；未来 CLI 若接入账号体系，钱包键随 `user_id` 走，见 §5 注。

### 2.7 资金守恒与幂等机制（实现岗必做，测试必钉）

1. **入账幂等键**：钱包流水 `ref` 唯一约束（逻辑层，非 DB 约束）：寄售单 id、拍品 id、死者角色 id（`death_sweep`）、`withdraw` 时间戳键。入账前查 `ref` 已存在→跳过并返回既有结果。
2. **保存顺序**：单据状态变更（SOLD／EXPIRED／FORFEITED／票清除）与钱包入账须在同一逻辑步内完成，先写钱包流水再保存单据终态；重放时单据已终态→跳过，流水 `ref` 已存在→跳过，双重防线。
3. **死行清零顺序**：钱包入账成功后再置 0 保存死行；若入账失败（仓储异常），死行保持原值、结算整体报错（不得出现「钱已入钱包、死行未清零」的中间态被后续流程当作成功）。
4. **提取守恒**：`/钱包提取 <n>` 须 `n` 为正整数、`n ≤ wallet`，成功时 `wallet -= n` 且 `角色 spirit_stones += n` 同步保存；任一保存失败则整体失败回显（不得只减一边）。
5. **审计口径**：`ChronicleRepository.record` 的资金归集大事记须含：死者名、归集合计、钱包余额终态；钱包流水 `note` 须含人类可读的单据说明（寄售品名／拍品名／死因）。
6. **sweep 合计口径（评审 S1，QA-D1 修订）**：`sweep` 明细的 `total` 定义为**本次实际入账额**＝实际入账的随身＋寄存＋实际入账的拍卖退款之和，与钱包增量一致（当票没收不计入合计——本金已在随身中；议政作废无金额）。`spirit`／`vault` 仍为清零前行内观测额：正常路径（首笔或残差入账）下 `total == spirit + vault + 退款合计`，与结算页明细加总一致；崩溃重放／ref 已存在而跳过的路径下，跳过部分计 0，`total` 小于观测额，差额见 `details["skipped"]`（`{kind, ref, amount, reason}`）。前端结算页合计行与大事记“资金归集 X 灵石”均用 `total` 口径。`auction_refunds` 只含实际入账的退款，跳过的退款不进该列表、只进 `skipped`。
7. **残差归集与双入口统一（评审 M1b，选定方案；QA-D1/D2 修订）**：CLI 与 server 双入口的已结算行补扫语义以 server 守卫为准——已结算行恒跑 sweep，仅当 sweep 确无真实变化（实际入账／作废／没收，见第 10 条）时返回 None；CLI 的 else 分支同款恒跑 sweep，是否打印【资金补扫】按同一真实变化判定（`core.wallet.sweep_has_real_change`），不再按毛额 `total`／退款列表打印。sweep 步骤②在 `death_sweep` ref 已存在但行内仍有余额时，先按第 10 条判首笔崩溃重放；不等时以残差入账：残差 ref 由（死者角色 id＋残差金额）派生（`{char_id}:residual:{spirit}:{vault}`），两次 sweep 之间新落入的、金额不同的残差→不同 ref→正常入账；残差 ref 已存在→残差崩溃重放，跳过不双记。残差是漏网付款的最后一道网，不是主路径——主路径上死行付款已全部改道钱包（超价退款见 §2.5 配套规则：上一领先者已死直接退其账户钱包，不退死行）。
8. **幂等窗口与 ref 格式（评审 S7／S8，仅文档化，不改 ref 格式与截断逻辑）**：钱包流水只保留最近 50 条，`ref` 查重窗口即这 50 条；旧 ref 落出窗口后，单据终态（SOLD／EXPIRED／FORFEITED／票清除）是第二道防线，重放时单据已终态即跳过。三种 `auction_refund` ref 各自对应互斥路径，不得混用：`{lot_id}`（死亡 sweep 退款，OPEN 单领先者已死时退钱包并回起拍）；`{lot_id}:outbid:{prev_id}`（超价退款，新出价取代旧领先者时退旧领先者）；`{lot_id}:settle-refund`（落槌兜底退款，未 sweep 的死者领先单到期落槌时退钱包、拍品按流拍计）。三路径互斥的理由：sweep 后单已回起拍（`bid_count` 归 0），到期不再走落槌退款；超价只发生在新出价瞬间；兜底只发生在到期且领先者已死且未 sweep 时。
9. **部分归集信号（评审 M5）**：sweep 的交易／拍卖／议政／当票四步异常不再静默吞掉——记日志并在返回 `details.errors` 中带 `{step, error}`，调用方（CLI 与 server 双入口）据此记一条 `WALLET_SWEEP_PARTIAL` 大事记；随身归集步（步骤②）异常保持上传，不得在 `death_settled` 置真后静默部分归集（即步骤②失败时结算整体报错，`death_settled` 不置真）。步骤异常本身不单独触发 server 已结算分支的 backfilled／CLI 的【资金补扫】打印（见第 10 条真实变化判定）。
10. **首笔崩溃重放识别与实际入账标志（QA-D2 必修、QA-D1 同批）**：`death_sweep` 流水条目须显式记录随身／寄存 breakdown——主口径为 `WalletEntry` 的 `sweep_spirit`／`sweep_vault` 显式字段（首笔与残差条目均写，且 `sweep_spirit + sweep_vault == amount`）；本字段上线前写入的旧条目两字段均为 0，兼容回退为解析其 note 中的「随身 X＋寄存 Y」（旧 note 由步骤②统一写出，解析失败视为 breakdown 未知、走残差逻辑）。步骤②：`death_sweep` ref 已存在、当前行内（随身，寄存）与已入账首笔 breakdown 完全相等、且 `death_settled` 为假→判定为崩溃重放：只清零行内余额、不入账，`details["replay"] = True`，跳过项记入 `details["skipped"]`（`reason = "crash_replay"`）；不等→走残差逻辑。`death_settled` 门限不可省：该标志真意味着道统结算已完成且死行已随结算保存，此后行内余额只可能是结算后新落入的钱，必须走残差——无门限时已结算行落入的同额新钱会被误判为重放而清零丢弃（QA-D1 CLI 用例即此情形）。`sweep_credited`／`residual_credited` 只在 `credit_wallet` 本次实际入账时置真（旧“尝试即置真”作废）。真实变化判定（server／CLI 同口径）＝`sweep_credited`、`residual_credited`、`auction_credited`（本次确有拍卖退款入账）、议政作废数、当票没收任一成立；无真实变化时 server 已结算分支返回 None、CLI 不打印【资金补扫】。**已知边界（不掩盖）**：其一，未结算但死行已清零保存、之后又落入同额新钱时，仍会被误判为重放而清零不入账（即该笔钱丢失而非双记），需“漏网付款＋同额＋中间恰好有一次 sweep（已清零保存但未结算）”三者叠加；其二，已结算行补扫首笔本身在“账户已保存、死行未保存”的极窄窗口（保存账户行与保存死行之间）崩溃时，重放因 `death_settled` 为真而走残差，可能双记。两者在现有状态（流水＋死行）下均不可区分：主路径死行付款已全部改道钱包，残差只是最后一道网，正常流程中几乎不出现，但属本方案接受的残余风险，不得谎称已彻底消除。

### 2.8 Web 界面三处（视觉与交互要点；沿用现有样式，不翻新）

1. **死亡结算页**（扩展既有 `deathModal`／`showDeath`，CLI 对应 `render_legacy_settlement` 扩展同款信息）：
   - 结构（自上而下）：死因与享寿 → 道统点与世数（既有）→ **资金归集明细表**（随身灵石／寄存灵石／拍卖退款（逐单：拍品名＋金额）／当票没收（物品名＋赎回价说明）／寄售待结提示（在售单数与「成交后入钱包」说明）／议政票作废提示）→ **账户钱包余额**（户名：`username`，金额）→ 建角表单（新道号＋加成选择，既有）→ 「暂不转世」次要按钮（既有语义：下次入世再转）。
   - 视觉：沿用 modal 现有配色与字体；金额右对齐、单位统一为「灵石」；明细表行间以细线分隔，窄屏自动折行；零项不隐藏、显示「—」（避免玩家误以为漏算）。
   - 交互：建角按钮文案须为动词明确的「以此道号重入轮回」；提交后按钮置灰防重复提交（后端幂等为第二道防线）。
2. **账户钱包展示**（`_status_dict` 新增 `wallet` 块＋前端命盘区钱包行；CLI 新增 `/钱包` 面板）：
   - 内容：户名（`username`）／余额／最近流水（最多 5 条：时间＋种类＋金额＋单据说明）／操作提示（`/钱包提取 <金额>`）。
   - 视觉：沿用命盘现有卡片样式；余额数字加粗，流水用 `muted` 小字；钱包行在命盘顶部货币区（灵石／寄存旁），不另开页面。
   - 交互：`/钱包提取` 失败（金额非法／超额）时回显明确原因且余额不变；成功时回显「钱包 −n／随身 ＋n／双余额终态」。
3. **死亡后建新角色的引导流程**（`deathModal` 的重生表单＋CLI 的 `prompt_reincarnation`）：
   - 引导文案三要素缺一不可：① 钱包余额与户名（「钱还在你的账户名下」）；② 新角出生灵石 150 不变（不制造「钱包被清空」的误解）；③ 提取指引（「入世后用 `/钱包提取 <金额>` 取用账户金额」）。
   - 交互：道号输入框保留既有默认值逻辑（空则沿用旧名规则，冲突时 `·转`）；加成选择上限提示沿用既有（至多 3 项）；表单提交失败时保留已填道号与已选加成（不清空重填）。

## §5 数据兼容与迁移方案

### 5.1 零改表兼容（默认即兼容）

- `LegacyAccount` 新增字段带默认值：旧 `player_legacy` 行 JSON 无 `wallet_stones`／`wallet_ledger` 时，pydantic 自动补 0／[]，首次 `save` 后自然带上新字段。**不得**写一次性全量改写脚本去碰所有账户行。
- `MarketListing` 新增 `seller_user_id = ""`：旧单 JSON 无此字段时自动补空串；`is_open` 等行为不变。
- `characters` 表、`accounts` 表、`world_state` 宗门／议政／版图 KV：结构不动。议政票清除是会话 KV 内的 `votes` 删键＋保存，不动会话结构。

### 5.2 迁移补扫（上线后首次触达时执行，幂等）

触发点（唯一 choke 点）：登录死者路径（web `/login` 死者 payload 前）与 `/转世`／CLI `ensure_alive_player`／`settle_and_reincarnate` 的资金归集步之前。凡命中以下任一条件即执行补扫（与 §2.3 同款步骤，`ref` 幂等保证与正常 sweep 不叠加）：

1. **已死未转世行**：角色行状态 DEAD（或寿尽）且 `death_settled` 已为真（旧规则已结算道统点）但钱包无对应 `death_sweep` 流水（`ref = 角色 id` 缺失）→ 补扫随身＋寄存、拍卖领先退款＋回起拍、议政票清除、当票没收。补扫后死行清零。
2. **已死未结算行**：`death_settled` 为假→走正常 §2.3 全流程（资金归集＋道统结算），无需特殊处理。
3. **寄售旧单回填**：`seller_user_id == ""` 的 OPEN 单，凡 `seller_id` 能命中现世角色行 id→回填该行 `user_id`；凡 `seller_id` 命中死行→回填死行 `user_id`（成交款路由到钱包，见裁定 1）；凡两者皆不命中→**不回填**，按 §5.3 封存规则处理，并在迁移报告中列出（单号／品名／标价／卖家名）。

### 5.3 旧单不可考封存规则（不得丢钱、不得重复记账的操作化）

- 买前路由预检（CLI 与 server 的买寄售 handler 共用）：成交前先解析付款路由——`seller_user_id` 可用→放行；`seller_id`／`seller_name` 能解析到存活角色且 id 一致→放行（生前旧口径）；死行→放行（款入该行账户钱包）；**三者皆无→拒售**，返回「此单卖家已不可考，天道暂封此单，买家未扣款」，且买家灵石分文不动（预检在 `buy_listing` 扣款之前）。
- 封存单的物品不删除、不没收、不改价，仅不可成交；迁移报告列出清单供 Martinez 定夺（GM 手动处理不在本 spec 范围，见 §3）。
- 成交写回（评审 M4）：买寄售成交时，成交路径（`complete_sale_payment`）把路由解析到的 `seller_user_id` 持久化写回旧单并保存；`resolve_sale_route` 本身保持纯读预检，不写盘（写回只在成交路径）。
- 本规则**仅适用于上线前已存在的无 `seller_user_id` 旧单**；上线后新单必有 `seller_user_id`，不再产生不可考单（`list_item` 写入时断言）。

### 5.4 诚实声明：不可追回的部分（实现岗不得以任何方式「补发」）

- **已转世覆盖的旧行**：旧行已被新角覆写，旧随身／寄存金额无任何结构化记录（`past_lives` 只有境界／死因／道统点，无金额字段）。这部分资金在旧规则下已随行消失，**迁移无法追回、不得凭空捏造补发**。迁移报告须明文列出「已转世账户数（仅计数，不估算金额）」并附本声明。
- **已消散的旧拍品／旧流拍物**：按旧规则已消散的拍品不恢复。
- **CLI 本地账户键**：CLI 钱包键为 `local_player_01`；若同一真人后来在 web 注册了正式账号，两者钱包**不合并**（不同 `user_id` 即不同账户）。合并账户不在本 spec 范围，须 Martinez 另行决策。

## §6 风险与实现岗注意事项

1. **双入口遗漏是最大风险**：钱包结算只进 CLI 或只进 server 都会导致另一端挂起资金永悬。实现后须用 T11＋T12 双端各跑一次死亡全流程对照。
2. **拍卖回起拍的语义变更须公示**：死者领先单回起拍后，拍品当前价回到起拍价（低于此前领先价）。这是本 spec 的有意选择（此前领先价对应的钱已退回，无人再持有该出价），前端拍品行须如实显示起拍价，不得沿用旧领先价展示。
3. **议政作废的公示**：场次面板在死者票被清除后，弟子投票计数须如实下降；不得为「好看」而保留死者票数。已结算场次则一律不动。
4. **并发**：server `World.handle` 持锁，死亡 sweep 与拍卖 `advance`／`settle_expired` 均在锁内或惰性推进中触发；实现岗须确认 sweep 与 `advance` 的互斥（不得出现 sweep 退款后 `advance` 又按旧 leader 落槌）。
5. **测试隔离**：新测试文件沿用 `tests/test_auction.py` 的做法（独立进程级隔离、真实仓储调用），不得读写开发用 lived DB；T15 迁移演练须用演练库，不得在真实存档上试跑。
6. **未决（须 Martinez 或实现评审拍板，不由实现岗擅自定）**：① 封存旧单的最终处置（长期封存 vs GM 清理）；② CLI 本地账户与 web 正式账号的合并问题（见 §5.4）；③ 钱包流水保留条数（本 spec 暂定最近 50 条，实现评审可调，但余额字段独立于流水的原则不动）。
