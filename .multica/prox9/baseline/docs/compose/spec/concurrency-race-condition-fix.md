# 规格说明：连续点击竞态防护与前置消耗状态单调锁 (concurrency-race-condition-fix)

## 1. 痛点问题 (Problem)
- **连续点击数据覆盖与回滚**：当道友在界面上连续点击交互时，若前置请求涉及 AI 叙事推演或耗时较长（2~8 秒），后置较快返回的请求所扣除的灵石、道具消耗或状态变更，会被滞后返回的前置请求所携带的旧状态快照（Stale State Snapshot）完全反向覆盖，造成“数据回滚/吞消耗/显示紊乱”。
- **前端交互缺乏全局互斥与防抖**：前端仅对底部输入框的个别按钮做了禁用，卡片与功能按钮（大荒探险、洞府设施、坊市地摊解石、金库等）未做统一节流拦截，用户连续狂点产生多重请求穿透。
- **本地乐观扣减与静默丢弃割裂**：前端在部分操作中先直接扣减了本地状态（如 `s.stones -= 20`），但随后调用的 `sendCmd` 因处于 `busy` 状态被直接静默丢弃，导致“前端表面扣了、后端未收到、稍后被慢速响应直接覆盖重置”。
- **服务端长耗时操作事务落账滞后**：服务端长耗时 AI 指令在等待 AI 响应的数秒内未先落盘前置消耗，导致并发读取或回写时状态滞后。

## 2. 总体设计方案 (Design)
1. **前端请求代际序号锁与单调更新 (Client Epoch Monotonic State Lock)**：
   - 客户端维护 `state.lastEpoch`（自增全局请求代际号）与 `state.appliedEpoch`（已落账最高代际号）；
   - 每次发起网络写请求（`/action`, `/chat` 等）分配递增 `reqEpoch`；
   - `applyStatus(st, reqEpoch)` 进行单调性校验：仅当 `reqEpoch >= state.appliedEpoch` 时才允许合并角色数据并更新界面；
   - 若 `reqEpoch < state.appliedEpoch`（滞后的过期慢请求），坚决丢弃其携带的旧 `status`，仅将文本叙事录入日志流，彻底斩断旧状态覆写最新数据的可能。

2. **全局水墨神念交互互斥锁与读写分离 (Jade Throttle Guard & Action Mutex)**：
   - 升级全局忙碌态管理，当处于写事务执行中时，拦截所有写操作触发点（探险、催熟、汲取、捡漏、还价、寄存等）；
   - 拦截时弹出古典仙侠水墨提示：“天道神念推演中，诸法暂滞，请稍候再降法旨”，杜绝狂点穿透；
   - 保持读写分离：只读操作（切换视图、查阅纳戒、翻看地图、研读日志）畅通无阻，避免僵硬死锁。

3. **客户端危险乐观扣减安全重构 (Safe Optimistic Deduction Refactoring)**：
   - 彻底废除“先在本地改 `s.stones` 随后调用可能被 `busy` 拦截丢弃的 `sendCmd`”的不安全模式；
   - 统一接入受控的网络执行管道，确保只有请求成功发出并确认时才落账，避免假性消耗与账目割裂。

4. **服务端前置消耗安全落盘与异常补偿 (Backend Pre-deduction & Compensation)**：
   - 在长耗时外部 AI 交互前（如 `core/adventure.py`），先原子扣除盘缠/前置成本并持久化保存；
   - 若外部 AI 调用发生网络中断或异常，启动补偿机制退还盘缠，并记录天道因果日志；
   - `_status_dict` 输出携带状态版本序号 `version`，与客户端 Epoch 形成双向单调保障。

5. **东方水墨纯正汉字铁律**：
   - 防重提示与等待反馈 100% 采用东方古典仙侠术语，严禁出现现代软件用词或英文。

## 3. 不在本次范围 (Out of Scope)
- 跨服分布式锁（当前单服/局域网服架构无需 Redis 等外部中间件，直接使用 Python 原生原子事务即可）。
