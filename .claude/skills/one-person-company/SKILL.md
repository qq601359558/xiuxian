# 一人公司开发编制 (One-Person Company)

本技能把一次开发任务组织成一家“一人公司”：一人分饰多岗，
但每岗有独立的职责、产出与禁止事项，岗与岗之间互相制衡，
避免“一个人写、一个人审、一个人说了算”导致的漏网缺陷。

## 适用范围与定位

- **只服务于本仓库的开发流程**，即《天道因果录》代码、文档、
  测试、版本与灰度发布工作。
- **不改变游戏内任何玩法规则**。寿元、境界、因果、天劫、经济、
  势力等数值与行为规则，仍以各功能 Spec 与 `core` 规则引擎为准；
  本技能无权新增、修改或 reinterpret 任何一条玩法规则。
- **不取代根目录 `AGENTS.md`**。`AGENTS.md` 是项目级强制流程
  （阶段一细化 → 阶段二受控开发 → 阶段三回归验证）；
  本技能是该流程的组织方式：谁在哪个阶段干什么、交付什么、
  过什么门禁。本技能与 `AGENTS.md` 冲突时，以 `AGENTS.md` 为准。
- **不取代 `requirement-evaluator`**。主策/需求官岗就是执行
  `requirement-evaluator` 五步推演的岗，本技能不另立一套需求
  分析方法；两份技能是“组织层”与“方法层”的关系，见下文
  “与 requirement-evaluator 的关系”。
- **不适用于游戏内 NPC**。这里的“多智能体”指开发过程的多岗
  协作，不指游戏内多智能体玩法或 NPC 组织形态。
- **双份存放惯例**：本文件在 `.agents/skills/one-person-company/`
  与 `.claude/skills/one-person-company/` 各存一份，内容必须
  完全一致；改动时两份同步改，改完用 `diff` 核对。

## 核心铁律（所有岗共守）

1. **寿元是硬通货**：1 游戏年 = 1 现实天；任何改动不得
   暗改寿元计量、消耗或结算口径。
2. **规则引擎裁决数值**：数值、因果、境界、天劫等判定以
   `core` 规则为准；LLM 只负责叙事与 NPC 言行/心智，
   不得由 LLM 直接决定数值结果。
3. **Spec 契约先行**：无 Spec 不写业务代码（机械小改除外，
   见“标准流程”第 1 步）；Spec 是验收的唯一依据。
4. **不在 `main` 上直接改**：业务改动一律走隔离 worktree，
   见“协作规矩”。
5. **无证据不称完成**：测试输出、命令输出、评审结论缺一不可；
   不得用旧输出或转述代替实测。

## 编制总览

| 岗 | 一句话定位 | 唯一对谁负责 |
|---|---|---|
| 总管 coordinator | 拆需求、定契约、派工单、汇总验收、唯一对用户负责 | 用户 |
| 主策/需求官 requirement | 用 requirement-evaluator 五步推演产出可验收 Spec | 总管 |
| 后端/规则工程师 backend | `core` 规则与存储，守核心铁律 | 总管（经 Spec） |
| 前端工程师 frontend | web 界面，守 CLI/Web 双端契约 | 总管（经 Spec） |
| 测试工程师 QA | 跨功能对账，缺陷落成必现用例 | 总管（独立于开发岗） |
| 评审官 reviewer | 只审不改，独立审 diff | 总管（独立于实现者） |
| 发布/运维 release | 版本、tag、灰度手册、推送核验 | 总管 |

同一人（同一 agent 会话）在一次任务里可以先后担任多岗，
但**同一批改动不能自己审自己**：评审必须由未参与该批
实现的独立视角完成（独立子代理或换岗后只审不改的重读），
且评审结论必须落字，不得口头“看过了”。

## 各岗专属描述

### 1. 总管（coordinator）

- **职责**：接收用户需求并拆成工单；定各岗的输入契约与
  截止门禁；汇总各岗产出写最终报告；是唯一对用户汇报、
  唯一有权宣布任务完成或叫停的岗；出现跨岗争议时裁决，
  裁决以 Spec 与 `AGENTS.md` 为准，不得凭个人偏好改规则。
- **输入**：用户原始需求；各岗的产出与门禁证据。
- **产出**：工单清单（岗 / 任务 / 输入 / 验收标准）；
  最终汇总报告（改了什么 / 证据 / 遗留问题 / 收尾选项）。
- **禁止事项**：
  - 不亲自写业务代码（只写工单、Spec 骨架以外的协调文档
    与汇总报告；确需补位时须先把总管职责交接并记录）。
  - 不得在评审 must-fix 未清、测试未过时宣布完成。
  - 不得绕过 Spec 直接给开发岗下“照我说的改”的口头指令；
    需求变更一律先回主策岗更新 Spec。
  - 不得同时担任同一批改动的评审官。

### 2. 主策/需求官（requirement-evaluator 执行岗）

- **职责**：按 `.agents/skills/requirement-evaluator/SKILL.md`
  执行五步推演（解构本质 → 可行性评估 → 不足与盲区 →
  举一反三 → 完善方案），把口头诉求收敛为“真正需求”，
  再落成一份可验收 Spec：`docs/compose/spec/<feature>.md`，
  含 Problem / Design / Out of Scope 与可独立验收的任务列表。
- **输入**：用户原始需求；仓库现状（相关模块、存量数据语义、
  历史 Spec）。
- **产出**：五步推演结论；真正需求条目（问题、行为契约、
  边界、验收标准、明确不做范围）；Spec 文档。
- **禁止事项**：
  - 禁止跳过五步推演直接给实现方案，更禁止在细化完成前
    写业务代码（`AGENTS.md` 阶段一）。
  - 禁止凭感觉扩写或缩水需求；Spec 外的功能一律进
    Out of Scope 或另立工单。
  - 禁止在 Spec 里写实现细节绑架开发岗（如指定私有函数名），
    只定行为契约与验收标准。
  - 禁止把未确认的关键决策写成已定论；需用户确认的点
    必须标出并走总管请用户确认（用户明确说“直接改”时除外，
    但仍须产出细化结论）。

### 3. 后端/规则工程师（backend / rules）

- **职责**：按 Spec 实现 `core` 规则、服务端逻辑与存储；
  行为变更优先补失败测试再实现；改动存档/数据语义时
  评估向前兼容并写清迁移影响。
- **输入**：Spec；隔离 worktree；相关模块现状。
- **产出**：实现代码 + 随改动新增/更新的测试；改动模块
  清单与兼容性说明。
- **禁止事项**：
  - 禁止在 `main` 上直接改；禁止跳过 Spec 写业务代码。
  - 禁止让 LLM 决定数值结果；禁止暗改寿元口径、
    境界/因果/天劫判定与经济数值。
  - 禁止为图省事改动未在 Spec 中的接口契约；确需改时
    先回主策岗更新 Spec。
  - 禁止提交“看起来对了”的代码：每个 Spec 验收条目
    须有可观察证据（测试或命令输出）。

### 4. 前端工程师（frontend）

- **职责**：按 Spec 实现 web 界面；守 CLI/Web 双端契约——
  同一行为在两端语义一致，后端返回字段缺失时前端不得
  自造默认值掩盖问题，应报给后端岗补齐。
- **输入**：Spec；后端接口契约；现有 web 界面现状。
- **产出**：界面改动 + 与之对应的可观察验证（页面/命令
  输出、双端一致性证据）。
- **禁止事项**：
  - 禁止在 `main` 上直接改；禁止跳过 Spec 写业务代码。
  - 禁止只改一端：涉及双端的行为须两端同步验证，
    另一端暂不改时须在 Spec 与报告中明写遗留项。
  - 禁止用前端展示层修正后端数值错误（掩盖而非修复）。
  - 禁止凭感觉定样式与文案覆盖 Spec 定好的行为契约。

### 5. 测试工程师（QA）

- **职责**：独立于开发岗做跨功能对账：经济账、寿元账、
  战力账、因果账、宗门账、状态机/幂等性、双端契约、
  存档兼容；每个缺陷必须落成可复现的必现用例
  （失败测试先行），并给出复现步骤、期望与实际、
  影响面与严重度；回归失败先修复再重跑，连续失败
  两次后停手重推根因，禁止硬改蒙混。
- **输入**：Spec；实现 diff；历史缺陷清单与已知易 flaky 点。
- **产出**：QA 报告（对账矩阵 / 缺陷清单 / 必现用例）；
  回归证据（测试命令与真实输出）。
- **禁止事项**：
  - 禁止凭感觉定性：无复现用例的缺陷不进清单，
    只记为“待复现线索”。
  - 禁止只测新功能不测旧功能；禁止用旧输出、他人转述
    代替自己跑的测试。
  - 禁止私自改业务代码修缺陷：缺陷一律回开发岗修复，
    测试岗只负责复现与验证修复。
  - 禁止把已知 flaky 测试的偶发失败静默放过：须记录、
    归因或单独立项。

### 6. 评审官（reviewer）

- **职责**：只审不改，独立审 diff，三个维度缺一不可：
  规格符合性（是否按 Spec 实现、有无超纲/缩水）、
  正确性（逻辑、边界、并发/幂等、数据一致性）、
  代码库一致性（命名、结构、既有契约与风格是否被破坏）；
  结论分三档：通过 / must-fix 清单 / 驳回重做，
  must-fix 须逐条写清位置与理由。
- **输入**：Spec；实现 diff；测试与 QA 证据。
- **产出**：评审报告（逐条结论 + must-fix 清单）。
- **禁止事项**：
  - 禁止直接改代码：发现问题只写 must-fix，不顺手改掉。
  - 禁止审自己写的改动；禁止无 Spec 评审（无 Spec 的
    改动先退回主策岗补 Spec，机械小改除外）。
  - 禁止只看增量不看涟漪：须评估对上下游模块、
    接口、存量数据的影响。
  - 禁止以“大概没问题”放行：不确定的点须标为
    待验证项并要求证据，不得含糊通过。

### 7. 发布/运维（release）

- **职责**：定版本与 tag；更新 CHANGELOG 与灰度手册
  （`docs/gray-runbook.md` 一类面向宿主的手册）；合并前
  核对分支与工作区干净度；推送后核验远端 head 与 tag
  与本地一致；发布后回归冒烟（关键路径跑通）并记录证据。
- **输入**：通过评审与 QA 的分支；版本规划；灰度手册现状。
- **产出**：版本号 + tag；CHANGELOG / 灰度手册更新；
  推送核验记录（本地与远端 head、tag 一致性）；
  发布后冒烟证据。
- **禁止事项**：
  - 禁止在评审 must-fix 未清、测试未过时发版。
  - 禁止只推分支不核验：推送后必须实查远端状态，
    不得以本地成功推断远端成功。
  - 禁止把未合入的改动、临时调试代码带入发布分支。
  - 禁止跳过灰度手册更新就发需要宿主操作的版本。

## 协作规矩

1. **Spec 契约先行**：主策岗产出 Spec 并经总管确认后，
   开发岗才能开工；开发中发现 Spec 缺口，先回主策岗
   修 Spec 再继续，不得边写边改契约。
2. **隔离 worktree**：业务改动在 `.worktrees/<slug>` 隔离
   工作区进行（用户明确指定路径或允许原地改时除外）；
   完成后经评审与 QA 再合并，禁止在 `main` 上直接改。
3. **谁写谁不审**：实现者不得担任自己改动的评审官；
   评审官只审不改，must-fix 回实现者修复后重审。
4. **评审 must-fix 全部修完**：must-fix 有一条未清即
   不得合并、不得发版；修完须重跑相关测试并由评审官
   确认关闭（逐条销账，不批量含糊关闭）。
5. **测试不过不合并**：回归失败、新增验收无证据、
   QA 缺陷未落必现用例并验证修复的，一律不合并。
6. **工单单向流动**：需求 → 主策（Spec）→ 开发（实现）
   → 测试（对账）→ 评审（审 diff）→ 发布（发版）→
   总管（汇总汇报）；返工时回到对应上游岗，不得跨岗
   私下改动（如测试岗不得直接改业务代码、评审官不得
   直接改代码）。
7. **证据留痕**：每岗产出须落字（Spec、测试输出、评审
   报告、QA 报告、推送核验），口头结论不算门禁证据。
8. **争议裁决**：跨岗争议由总管按 Spec 与 `AGENTS.md`
   裁决；裁决结果写入 Spec 或报告，不得留口头约定。

## 启动一个开发任务的标准流程

| 步 | 岗 | 交付物 | 门禁（不过不进入下一步） |
|---|---|---|---|
| 1. 细化 | 主策 | 五步推演结论 + 真正需求条目 | 需求含糊点已收敛或已标出待确认项；机械小改可只留细化结论 |
| 2. Spec | 主策 + 总管确认 | `docs/compose/spec/<feature>.md` | 含 Problem / Design / Out of Scope 与可独立验收的任务列表；关键决策已确认（或用户已授权直接改） |
| 3. 实现 | 后端 / 前端 | 隔离 worktree 中的代码 + 新增测试 | 在 `main` 外开发；行为变更有失败测试先行；每条验收有证据 |
| 4. 验证 | 开发 + 测试 | 相关 pytest 与关键路径输出 | 相关套件通过；基线失败须标注 `PRE-EXISTING`；失败先修再重跑 |
| 5. 独立评审 | 评审官 | 评审报告 | 只审不改；must-fix 全部修完并逐条销账，否则不合并 |
| 6. QA | 测试 | QA 报告（对账矩阵 + 缺陷必现用例） | 跨功能对账完成；缺陷均已复现、修复、验证；回归通过 |
| 7. 发版 | 发布 | 版本 + tag + CHANGELOG / 灰度手册 + 推送核验 | 远端 head 与 tag 已实查一致；发布后冒烟通过 |
| 8. 汇报 | 总管 | 汇总报告 | 一次性汇报：改了什么 / 证据 / 遗留问题 / 收尾选项；用户另有汇报节奏要求时从其要求 |

说明：

- 第 1–2 步对应 `AGENTS.md` 阶段一；第 3–4 步对应阶段二
  implement/verify；第 5 步对应阶段二 review；第 6 步与
  阶段三回归验证重叠时合并执行、不重复造报告，
  但 QA 对账矩阵与评审报告不得互相替代。
- 单文件、无设计面、纯机械小改：可跳过完整流程，
  但仍须完成第 1 步细化结论 + 第 4 步验证，且须由
  总管在报告中注明“小改路径”。
- 返工规则：评审或 QA 发现问题，回到第 3 步修复，
  再依次重过第 4–6 步；Spec 本身有问题，回到第 2 步。

## 与 requirement-evaluator 的关系（无冲突声明）

- `requirement-evaluator` 管“怎么想”：五步推演方法。
- 本技能管“谁来干、按什么顺序干、过什么门禁”：
  主策岗就是 requirement-evaluator 的执行者，
  本技能不复制、不修改、不绕过其五步法。
- 触发关系：用户提新需求 → 本技能派主策岗 →
  主策岗激活 requirement-evaluator → 产出 Spec →
  后续岗按本技能流程推进。两技能的产出物（推演结论、
  真正需求、Spec）是同一条链上的前后环节，不是两套
  平行标准。
- 若 requirement-evaluator 未来更新，本技能的主策岗
  描述自动跟随新版执行，不以本文件为准复述旧方法。

## 任务收尾检查单（总管汇报前逐项打勾）

- [ ] Spec 状态已更新，Out of Scope 未被偷偷实现
- [ ] 所有评审 must-fix 已逐条销账
- [ ] 回归证据为本次实测输出，非旧输出或转述
- [ ] 改动模块清单与接口契约影响已列出
- [ ] 版本 / tag / CHANGELOG / 灰度手册（如需）已更新并核验
- [ ] 遗留问题与已知 flaky 点已写入报告，未隐瞒
- [ ] 工作区与分支已收尾（worktree 清理、分支去留有交代）
